# Snake NN Lab

**DSH 辅助从零实现神经网络与策略梯度训练器，让贪吃蛇自己学会觅食、躲避与猎杀。**

约 **2.1 万行 C++**（89 个文件）+ **8000 行设计文档与实验日志**。
不依赖任何机器学习框架 —— 矩阵、激活、softmax、反向传播、优化器全部重新实现。

> **技术关键词**：反向传播 · 数值梯度校验 · REINFORCE / Actor-Critic + GAE ·
> 确定性仿真与轨迹复现 · X-Macro 配置代码生成 · 空间哈希碰撞检测 · 单帧 O(1) 视野光栅化 ·
> 分层架构与单一事实源 · AI 辅助工程方法论

更多文档见 dosc 和 devlogs。

## 一、项目概述

### 1.1 这是什么

一个**强化学习实验平台**，以贪吃蛇为训练环境。代码库包含四部分：

| 组成部分       | 说明                                                         |
| -------------- | ------------------------------------------------------------ |
| **神经网络库** | MLP 实现，不依赖任何机器学习框架。矩阵运算、激活函数、softmax、反向传播、参数初始化、优化器全部自行实现 |
| **强化学习栈** | 观测编码、策略网络、价值网络、轨迹缓冲、梯度更新、奖励结算、权重存档 |
| **游戏客户端** | 基于 SFML 的可视化程序：3 种玩法模式，以及一个可实时观察训练过程并现场调整超参的训练模式 |
| **诊断工具集** | 10 个可独立运行的 C++ 工具：单元自检、性能剖析、世界指纹回归、观测转储、学习链路验证 |

### 1.2 为什么不用现成框架

三个目的：**验证原理、获得完全控制权、保证可复现**。

- **教学目的**：反向传播必须亲手推导并实现一遍，才能确认自己理解的是数学而不是 API
- **控制权**：训练循环内部的每一个量（梯度范数、优势分布、策略熵、logit 尺度）都可直接观测与干预，
  这在"训练不收敛"的排查中是不可替代的
- **可复现**：整个仿真在固定种子下完全确定，可用于逐字节回归比对

### 1.3 外部依赖

| 依赖          | 版本             | 用途             |
| ------------- | ---------------- | ---------------- |
| MinGW-w64 GCC | 13.1.0           | C++17 编译器     |
| CMake         | ≥ 3.16           | 构建系统         |
| SFML          | 2.6.x (MinGW 版) | 窗口、图形、输入 |

## 二、怎么用（操作说明）

### 2.1 构建

双击 `build.bat`（首次约 1~2 分钟，之后增量编译几秒）。

它会依次做三件事：定位工具链 → 配置 CMake → 编译 7 个目标。
工具链路径可用环境变量覆盖，优先级为 **命令行 > 环境变量 > 内置默认**：

```bat
set CMAKE_EXE=D:\CMake\bin\cmake.exe
set MINGW_ROOT=D:\mingw64
set SFML_ROOT=D:\SFML-2.6.2
build.bat
```

构建产物、运行资源（`assets/`、`config/`、`saves/`）与依赖 DLL 全部落在 `build/`，
项目根目录不产生中间文件。**整个文件夹可以整体拷到任意位置**：若连 `build/` 一起拷贝，
`build.bat` 会检测到 `CMakeCache.txt` 里记录的是旧路径（CMake 缓存存的是**绝对路径**），
自动丢弃过期缓存并重新配置，无需手工删除。

### 2.2 启动

双击 `run.bat`。它把工作目录切到 `build/` 后再启动游戏，因此无论从哪里调用，
`config/`、`saves/`、`assets/`、`train_metrics.csv` 都定位到同一处。

> 也可以直接双击 `build\snake_game.exe`。但**不要**用其它方式改变工作目录后启动，
> 否则上述资源会去项目根目录找。

### 2.3 界面结构

```
主菜单 ─┬─ 开始游戏 ─→ 模式选择 ─→ 对局设置 ─→ 对局
        ├─ 训练模式 ─→ 训练设置 ─┬─ 队伍设置
        │                        └─ 实时训练
        ├─ 训练数据（读 train_metrics.csv 画曲线）
        ├─ 设置（全部游戏参数，分页编辑）
        └─ 退出
```

| `↑` `↓`          | 上下选择                           |
| `←` `→`          | 调整当前项的值（或左右切换标签页） |

## 三、世界模型与运行流程

### 3.1 单帧执行序列

`Arena::step(dt)` 是全项目**唯一**的世界推进实现，七个阶段按固定顺序执行：

```
0  食物速率    按当前存活蛇数换算本帧的生成速率
1  移动        每节位置按朝向推进（含转向缓动）
2  碰撞        墙 / 蛇-蛇（头撞身体致死、头对头双亡） / 吃食物
3  饥饿        距上次进食超过 starvationTime 则死亡
4  死亡结算    死亡蛇身转换为尸体食物（每条蛇只处理一次）
5  感知 + 决策  为每条蛇构建 Perception，再调用注册的 Brain 产生 Action
6  食物更新    按速率生成、超时清理、圈的调度与重定位
```

训练器与游戏客户端调用同一个 `step()`。阶段顺序是硬约束——例如"感知必须在决策之前"、
"圈的位置更新必须在感知与食物生成之前"；顺序错误会导致观测与奖励时序错位。

### 3.2 视野网格（`brain/VisionGrid.h`）

以蛇头为中心的 **32×32 网格，格边长 32px（视野 1024×1024px）**，随蛇头朝向旋转，
因此"左前方有障碍"始终对应网格中的同一片区域，网络无需自行学习旋转不变性。

每格为一个 8 位掩码，可同时表达多种语义：

```
0x01 墙        0x08 敌方蛇身    0x20 队友蛇身
0x02 普通食物   0x10 敌方蛇头    0x40 队友蛇头
0x04 尸体食物                    0x80 自身蛇身
```

射线查询通过掩码参数化：`BLOCK_MASK_NO_ALLY` 排除队友，与真实碰撞规则一致
（队友之间可互相穿过）。

### 3.3 感知输出（`brain/Perception.h`）

感知分三条通道：

| 通道     | 内容                                                   | 特点                                 |
| -------- | ------------------------------------------------------ | ------------------------------------ |
| 网格     | 32×32 位掩码                                           | 量化，但支持空间查询                 |
| 辅助列表 | 视野内其他蛇（按距离排序）、队友（全局，不受视野限制） | 精确坐标、朝向、长度                 |
| 食物圈   | 全部食物圈的方位、距离、食物数                         | 全局信息（圈是地图结构，非视觉对象） |

`Perception` 由 `Agent` 持有并复用，`clearLists()` 只清空不释放容量，预热后热路径零堆分配。

### 3.4 确定性保证

所有随机来源统一由**世界种子**驱动：

| 随机源                       | 实现                                          |
| ---------------------------- | --------------------------------------------- |
| 出生位置、出生朝向、食物位置 | 全局 `rand()`，由 `Arena::reset` 统一 `srand` |
| 圈的轮换顺序                 | `ZoneSchedule::orderSeed` 的确定性哈希        |
| 圈的坐标                     | `ZoneLayout::posSeed` 的确定性哈希            |
| 神经网络初始化               | `std::mt19937` + 显式种子                     |

训练与游戏**每局推进一格种子**（`seed = 基准种子 + 局号`），因此出生点、食物分布、圈位序列每局不同；
而"第 k 局"在给定基准种子下完全可复现，对照实验仍可比较。回归工具使用固定种子，关闭推进。

## 四、模块说明

### 4.1 神经网络（`src/nn/`，789 行）

```
matrix.h       矩阵与向量：行主序存储、运算符重载、乘法顺序按缓存友好排列
activation.h   tanh / ReLU / sigmoid 及其导数。导数一律以【激活前的 z】为输入
loss.h         softmax（含数值稳定处理）、交叉熵、softmax+CE 梯度、argmax、MSE
network.h      任意层数 MLP：前向缓存、反向传播、三种初始化、动量 SGD、
               梯度累加与缩放、参数遍历、权重存取
```

设计要求：

- **`backward()` 采用累加语义**。标准调用序列为
  `zeroGrad()` → 逐样本累加 → `scaleGrad(1/N)` → `step(lr, momentum)`，
  使批大小与学习率解耦。
- **`forEachParam` 统一遍历全部参数**。数值梯度检查、梯度裁剪、权重统计均通过该接口实现，
  新增层时无需修改这些通用逻辑。
- **初始化方式可对照**。`nn_selftest` 的第 6 项用同一任务对比 `U(0,1)` 与 Xavier：
  `U(0,1)` 的方差与 `fan_in` 无关，一层 16 个输入相加会把方差放大 16 倍、均值抬高 8，
  `tanh` 立即饱和、梯度消失；Xavier 按 `1/fan_in` 缩放可维持信号尺度。

### 4.2 强化学习栈（`src/rl/`）

| 文件              | 职责                          | 关键技术                                            |
| ----------------- | ----------------------------- | --------------------------------------------------- |
| `encoder.h`       | 观测编码（33 维）与动作编解码 | 训练与推理的唯一编码来源                            |
| `Trainer.h`       | 轨迹缓冲与梯度更新            | 策略梯度、Actor-Critic + GAE、熵正则、参数 EMA 基线 |
| `EpisodeRunner.h` | 单局流程与奖励结算            | 11 项奖励的有序结算、目标切换保护                   |
| `TrainTask.h`     | 任务预设与全部超参            | 单一配置来源                                        |
| `Checkpoint.h`    | 权重存档与列表                | UTF-8 路径处理（支持中文文件名）                    |

**观测向量（33 维）**

```
[ 0.. 3]  4 方向【墙 / 自身身体】射线距离
[ 4..11]  8 方向【敌方身体 / 蛇头】射线距离
[12..19]  8 扇区最近食物距离（归一化，无食物为 1）
[20]      速度 / 最大速度          [21]     长度 / 60
[22..23]  朝向 sin / cos
[24..26]  当前活跃圈：sin(方位) / cos(方位) / 距离
[27..29]  下一个活跃圈：sin(方位) / cos(方位) / 距离
[30..32]  最近队友：前向偏移 / 右向偏移 / 队友数量
```

设计要点：

- **障碍射线拆成两个通道**。早期版本把墙、敌方身体、自身身体按位或进同一组格子，
  网络无法区分"前方是墙"与"前方是蛇"，而两者的正确反应相反。现拆为 4 方向墙射线与 8 方向敌方射线。
- **圈只编码"当前"与"下一个"**，与世界中有几个圈无关。第 3 维为到圈心的归一化距离，
  而非"是否轮到它"的常量标记——后者不携带信息。
- **队友不算障碍**，因为队友之间可互相穿过。
- **帧堆叠（`STACK_FRAMES`）当前为 1，即关闭。** 开启后网络输入维度为
  `33 × STACK_FRAMES`，可获得速度与加速度等时序信息，代价是参数量与训练难度上升
  （实测堆到 3 帧即 87 维后训练明显变差）。

**动作空间（6 个离散）**

```
0 1 2 = 左转 / 直行 / 右转（普通速度）
3 4 5 = 左转 / 直行 / 右转（加速）
```

**学习器**

|          | `Baseline`         | `Critic`                                                     |
| -------- | ------------------ | ------------------------------------------------------------ |
| 优势估计 | `G − 滑动平均基线` | GAE，由第二个 MLP 估计 `V(s)`                                |
| 方差     | 高                 | 低                                                           |
| 代价     | 实现简单           | 每局需额外若干 epoch 训练 critic；GAE 的 λ 需在偏差与方差间权衡 |

超参：`γ = 0.99`、`lr = 0.02`、熵系数 `0.1`、ε-greedy `0.05`。

**奖励项（11 项，`TrainTask.h` 为唯一来源）**

```
① 死亡        −10.0        ② 吃到食物     +3.0（按实际得分折算）
③ 饥饿        0 → −3       ④ 吃饱余韵     +2.5 → 0（10 秒内递减）
⑤ 脱离危险    +1.35/次     ⑥ 贴近敌方身体 −21 × 距离渐变
⑦ 猎杀优势    +0.15/帧     ⑧ 击杀         +5.0
⑨ 尸体食物    分值高于普通食物            ⑩ 原地位移     −3.0/帧
⑪ 贴墙 / 贴敌 −21 × 距离渐变
```

设计约束：

- **不设存活奖励**。存活奖励奖励的是时间而非动作，会导致"原地不动"成为最优策略。
- **差分式塑形项在闭合回路上净和为零**，因此不能依靠它惩罚无效行为；⑩ 专门处理该问题。
- ⑪ 类惩罚采用距离渐变而非硬阈值。硬阈值会制造"阈值外任意方向等价"的平坦区域，
  策略会停在原地。

### 4.3 世界与实体（`src/arena/`、`src/entities/`、`src/sim/`）

```
Arena.{h,cpp}        世界推进的唯一实现；持有 agents / 食物 / 圈 / 碰撞系统
entities/Snake       蛇的几何、移动、转向缓动、体节、饥饿、加速
entities/FoodManager 食物生成、超时、圈内生成、尸体转换
entities/FoodZone    圈布局（ZoneLayout）与调度（ZoneSchedule）
sim/SpatialGrid      均匀空间哈希网格，供碰撞查询使用
systems/CollisionSystem  墙 / 蛇-蛇 / 食物 三类碰撞判定
```

**转向模型**：蛇的转向是缓动的，目标角度需按 `getSteerLead(steer, dt)` 计算，
否则实际角速度仅为设定值的 `1/(turnEase × dt)`。该函数是全项目唯一的动作→角度换算实现。

**圈调度**：

```
 0s ───────────── 6s ────────── 9s ───────── 14s ────────── 23s
 │←── 只有活跃圈 ──→│←──── 预告期 ────→│←─ 空窗 ─→│← 新活跃圈供食 ─→
                     ↑ 预告圈出现（供食还剩 3s）
```

- 圈的位置每轮重新随机选取，与上一圈的距离约束为地图短边的 40%~60%
- 预告圈与下一轮的活跃圈为**同一槽位、同一坐标**，换轮时仅改变显示状态
- 从预告出现到开始供食共 8 秒（3 秒预告 + 5 秒空窗），最远距离需 7.2 秒

### 6.4 学习链路自证：如何证明实现的反向传播是正确的

不靠读代码，而靠**答案已知的问题**。

`bandit_check` 构造一个 6 臂老虎机（第 2 臂 μ 最优，全随机基线 16.7%），
使用**与 `Trainer` 完全相同的**网络类型与梯度四步去解它：

```
最终 argmax        : 2  (最优是 2)  ✅
最终 p(最优臂)     : 0.9999
选最优臂占比(全程) : 99.7%   (全随机应为 16.7%)
判定: ✅ 学习器【正确】—— 所以「蛇学不会」不是梯度算错。
```

`bandit_check` 单独尚不充分：它的输入是常量，最优策略是一个常量输出，
**无法证明网络是否利用了输入**。因此补充 `statebandit_check`（上下文老虎机，
`ctx=0` 时最优臂为 2、`ctx=1` 时为 4，即最优策略**必须**是条件策略）：

```
最终 ctx=0 的 argmax : 2  (最优 2)  ✅
最终 ctx=1 的 argmax : 4  (最优 4)  ✅
全程选对率           : 99.5%   (全随机 = 16.7%)
判定: ✅ 网络【能】学会条件策略（输入不同 → 动作不同）。
```

这两个实验的方法论价值在于**把无法判定的大问题降解为可以判定的小问题**：
"蛇为什么学不会"无法直接回答，但"学习器实现是否正确"与"网络能否利用输入"可以。
两者都通过之后，排查方向就从"怀疑梯度实现"转向"环境设计 / 信用分配 / 方差"。

## 七、性能工程

### 7.1 性能探针

`bench_sim` 不是简单的计时脚本，而是可对照的性能探针：多个负载档位，
并对每个档位给出无感知开销的上界参考。

| 场景                         | 单线程帧率  | 感知占比 |
| ---------------------------- | ----------- | -------- |
| 9 蛇 × 12 节 / 60 食物       | 25314 帧/秒 | 50.9%    |
| 9 蛇 × 50 节 / 600 食物      | 10275 帧/秒 | 51.9%    |
| 重载（8000×8000 / 600 食物） | 1600 帧/秒  | 74.8%    |

感知是头号开销，且在负载越高的场景中占比越大（这是符合预期的：
感知的复杂度随蛇数与食物数增长，而其它系统的增长更慢）。

### 7.2 标墙的解析解法（`agent/VisionGrid.h`）

朴素实现是遍历视野网格的每格、把格心变换到世界空间、逐格判断是否越界，共 1024 次判断。

优化依据：地图是凸矩形，视野网格的每一行在世界空间中对应一条**直线段**，
因此"这一行中哪些格位于地图内"必然是**连续区间**。于是问题转化为
四条半平面约束在线段上的参数区间求交：

```cpp
// 对每行求 t ∈ [0,1] 的可行区间，一次得到整行的起止格号
// 1024 次逐格判断 → 32 次按行计算
```

优化后用 **400 组随机位姿 × 409600 格的全量对拍**证明与朴素解逐格等价
（`bench_sim` 的"标墙对拍"项），排除"更快但算错"的可能。

### 7.3 其他优化

| 手段             | 位置                            | 效果                                 |
| ---------------- | ------------------------------- | ------------------------------------ |
| 均匀空间哈希     | `sim/SpatialGrid.h`             | 碰撞只查邻近格，不遍历全表           |
| 感知缓冲区复用   | `agent/Agent` 持有 `Perception` | 热路径零堆分配                       |
| 矩阵乘法循环顺序 | `nn/matrix.h`                   | 按行主序调整遍历顺序以提升缓存命中   |
| 固定步长逻辑     | `core/Game`                     | 与渲染帧率解耦，避免 dt 抖动影响训练 |

### 7.4 已知的可优化空间

- **环境未并行化**。采样是训练吞吐的瓶颈，当前为单线程。机器有 6 个可用核心，
  多进程采样 + 参数服务器式归并可将吞吐提升数倍。`EpisodeRunner` 已具备
  "给定种子即可复现"的性质，是并行化的前提条件，但尚未实施。
- 推理未做批处理（当前 batch = 1）。
- 权重与配置的读写未做增量保存。

## 八、AI 辅助工程

这个项目的绝大部分代码、全部排查实验、以及 8000 行设计文档与开发日志均由人机协作完成。
值得单独成节，因为**"用 AI 高效写工程"与"用 AI 写一个 demo"是两件不同的事**。

### 8.1 核心矛盾：生成速度远超审查速度

AI 的代码生成速度远高于人逐行审查的速度，因此真正的瓶颈不是**生成**，而是**验证**。
所有有效的方法都指向同一件事：**把人的验收转化为机器可以自动判定的检查**。

### 8.2 六条可复用的方法

#### ① 先建立验证矩阵，再让 AI 动手

`CLAUDE.md` 中固化了一张硬性对照表（内容见 §5.4 验证矩阵），
写明"改了什么必须跑什么"。

它的作用是：把"这个改动有没有破坏别的东西"从主观判断变成 `exit code`。
在 AI 承担大部分编码工作的前提下，这张表是唯一能防止回归悄悄溜进代码库的机制。

#### ② 唯一实现清单：AI 编码最大的风险

**AI 最危险的行为是无意识地写出第二份实现。** 它看不到全局，于是"顺手再写一个编码函数"
是很自然的事。本项目为此付过真实代价：

- 观测编码曾存在一份"看起来一样"的拷贝，实测 **240 万次比对中最大差异 0.96**
- 绘制食物圈的渲染代码有**三处**，修 bug 时只改了一处（而用户看到的正是漏掉的那一处）
- 圈的位置更新逻辑被错置到"配置级生命周期"，导致每局圈位根本不变

因此 `CLAUDE.md` 中维护了一张「唯一实现」清单（世界推进 / 观测编码 / 梯度更新 / 一局与奖励 /
任务参数 / 存档 / 感知 / 字体），并配一条硬规则：**加功能前先确认这件事没有第二份实现。**

#### ③ 让 AI 造工具，而不是让它反复试

本项目的排查全部依赖**自建探针**，而非"改一版再看看"：

| 工具                                 | 解决的问题                                               |
| ------------------------------------ | -------------------------------------------------------- |
| `replay_check`                       | 重构有没有改变世界行为？→ 确定性指纹逐字节比对           |
| `bench_sim` 的标墙对拍               | 解析法优化和朴素实现等价吗？→ 400 例全量比对             |
| `train_probe --dump-obs`             | 策略到底看到了什么？→ 输出观测向量 + 圈的可见性时间线    |
| `bandit_check` / `statebandit_check` | 学习链路是否正确？→ **构造一个已知最优解的最小问题**去问 |
| `sens_check` / `perturb_check`       | 训练出的网络在算什么？→ 喂极端输入看 argmax              |

`bandit_check` 尤其值得说明：与其争论"梯度是不是写错了"，不如构造一个
**答案已知的多臂老虎机**，用**同一份**网络与梯度四步去解它——跑出 99.7% 选中最优臂，
即可判定学习器实现正确（详见 §5.5）。

#### ④ 把决策与教训写入文件，因为 AI 没有跨会话记忆

| 载体               | 内容                                                         |
| ------------------ | ------------------------------------------------------------ |
| `CLAUDE.md`        | 给 AI 的项目契约：铁律、唯一实现清单、验证矩阵、可移植性约束 |
| `docs/`（13 篇）   | 每个模块的**设计理由**，而不只是用法                         |
| `devlogs/`（8 篇） | 踩过的坑、被推翻的假设、实测数据                             |

这些文件的作用是**让下一次会话的 AI 不需要重新推导**，也不会重犯同一个错误。
例如"`.bat` 文件必须保持纯 ASCII"（cmd 按 OEM 代码页读取，UTF-8 中文会被当作命令执行）——
这条经验如果只存在于某次对话中，下一次必然重踩。

#### ⑤ 人机分工需要显式约定

| 交由 AI                                      | 留给人                                     |
| -------------------------------------------- | ------------------------------------------ |
| 编译、运行控制台工具、采集数据、执行回归比对 | **可视化验收**（观察画面判断行为优劣）     |
| 实现、重构、编写探针、撰写文档               | **设计决策**（奖励如何设计、玩法如何定义） |
| 批量机械修改（如 11 处调用点统一替换）       | **判断某个改动是否值得做**                 |

该分工来自实测：让人截图再让 AI 识别图像，效率远低于人直接观察画面；
而让 AI 运行 300 局训练并统计数字，效率远高于人手工完成。

#### ⑥ 禁止从统计量直接跳到"机制是 X"

这是整个项目代价最高的一条教训。在一次根因排查中，连续提出 **8 个假设，全部被数据推翻**：

| 假设                                | 推翻它的实验                                    | 结果                           |
| ----------------------------------- | ----------------------------------------------- | ------------------------------ |
| 熵正则系数过大，主导了梯度          | 实测 `entGradNorm / gradNorm`                   | **0.1%**，假设不成立           |
| 吃饱余韵在向梯度中注入噪声          | 奖励消融 `--ablate no-fed`，5 个种子            | 关闭后**全线更差**，假设不成立 |
| 梯度尖峰把权重打飞                  | 梯度裁剪，多组配置                              | **无改善**                     |
| 学习率过大                          | `--lr 0.005` ± 裁剪                             | **无改善**                     |
| `tanh` 饱和吃掉了回传梯度           | 将首层权重放大 1~8 倍                           | 仍学不会                       |
| 观测与奖励时序错位                  | 逐步核对 `Arena::step` 与 `EpisodeRunner::tick` | **完全对齐**                   |
| ε-greedy 随机步造成 off-policy 偏差 | 代码审查 + 修复                                 | 是真问题，但**不是主因**       |
| 反向传播算错                        | `bandit_check` 已知最优解                       | **学习器正确**                 |

共同的错误模式是：**从一个间接统计量直接跳到"机制是 X"，而没有先构造能直接判定 X 的最小实验。**

正确顺序是：**先造出能直接测 X 的工具，再看 X 是否成立。**
这条现已写入 `CLAUDE.md` 的接手须知。

### 8.3 AI 协作自身的失误记录

| 失误                             | 后果                                                         | 现行的做法                                                   |
| -------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **脚本批量改文件时锚点写错**     | 一次删除了整个 `Arena::reset()` 函数，并制造出**递归调用自身**的缺陷 | 脚本改完**立即**校验括号平衡并重新编译；能用 `edit` 就不用脚本 |
| **过滤构建日志时滤掉了关键错误** | 链接失败（exe 被占用）被 `grep error` 漏掉，多花数轮排查     | 构建输出中 `error` / `cannot open` / `Permission denied` 一并匹配 |
| **读数来源错误导致假结论**       | 用"某条蛇最后一次决策的观测"验证"当前可见性"，读到的是**死前冻结值** | 读取"当前世界"必须**现算**，不借用任何缓存                   |
| **把注释中的文件名当作 include** | include 插入静默失败，直到编译才暴露                         | 正则匹配 `#include "..."`，而不是裸文件名                    |

> **小结**：AI 能把实现速度提升一个量级，但**它同时会把"验证"变成新的瓶颈**。
> 因此真正有效的投入是——**验证基础设施、单一事实源、把决策写入文件**。
> 这三件事做齐之后，AI 才能在数万行代码上安全地执行重构。

## 九、设计基础

以下机制支撑了前面所有模块，也是长期维护中成本最低、收益最高的部分。

### 9.1 X-Macro 配置代码生成（`src/core/GameConfigFields.h`）

28 个配置字段由**同一张表**生成三样东西：结构体成员、配置解析、配置写回。

```cpp
#define GAME_CONFIG_FIELDS(X_FLOAT, X_INT, X_BOOL)   \
    X_FLOAT(mapWidth,  map_width,  3000.0f)          \
    X_FLOAT(snakeSpeed, snake_speed, 250.0f)         \
    ...
```

该头文件**故意不加 include guard** —— 需要在同一个翻译单元里被展开多次。
效果是"加了字段但忘了存 / 忘了读"这类不一致**在结构上无法发生**。

### 9.2 分层与依赖方向

```
utils → nn → rl ─┐
                 ├→ brain → agent → arena → entities / sim / systems → scenes → core(main)
                      ↑                                              ↑
                  算法层（可无窗口运行）                        渲染与交互层
```

硬性约束（改动时不可违反）：

- `src/nn/` 只依赖标准库
- `src/rl/` 只依赖 `nn/` 与标准库
- `src/brain/` 与 `src/rl/` **禁止** include SFML 头文件，也禁止 include `entities/`、`scenes/`、`systems/`
- 只有组合根 `main.cpp` 允许同时看到算法层与仿真层
- 新增算法 = 写一个 `Brain` 子类 + 在 `registerBuiltinBrains()` 加一行，**UI 代码无需改动**

### 9.3 确定性与回归

`replay_check` 是"缺乏语义保护的重构"的解法：

```
固定配置 + 固定种子 + 固定动作序列  →  每 N 帧输出一行世界状态 + 全剧累积哈希
```

`manual`（手写参考循环）与 `arena`（重构后的真实实现）必须**逐字节相同**。
当前哈希：`ce7d8b6c6a5ecbe1`。

`randomzones` 模式逐秒、并逐帧（换轮前后）输出圈的坐标与调度下标，
用于定位"预告圈未变成活跃圈"这类只持续 1~2 帧的缺陷。

### 9.4 可移植性

整个文件夹**拷贝到任意位置都能构建运行**。为此消除了 4 处硬编码：

| 原本的硬编码           | 现在的做法                                                   |
| ---------------------- | ------------------------------------------------------------ |
| 工具链路径             | `MINGW_ROOT` / `SFML_ROOT`（命令行 > 环境变量 > 默认）+ `cmake/Toolchain-mingw.cmake`。编译器与 `mingw32-make` 必须在 generator 校验**之前**生效，写在 `CMakeLists.txt` 里就已经太晚 |
| `C:/Windows/Fonts/...` | `assets/fonts/simhei.ttf` 随包 + `textutil::loadGameFont()` 候选链。此前 11 个场景各自写死系统字体路径 |
| `run.bat` 的相对路径   | 用 `%~dp0` 推导绝对路径，从任意工作目录调用均正确            |
| 脚本文件的字符编码     | `.bat` / `.ps1` **一律纯 ASCII**。cmd.exe 按 OEM 代码页读取，PowerShell 5.1 按 ANSI 读取，UTF-8 中文会被误解码为命令并执行 |

### 9.5 构建产物布局

所有中间文件与运行资源集中在 `build/`，项目目录本身不产生编译副产物：

```
build/
├── *.exe                7 个可执行目标
├── *.dll                SFML 及各依赖 DLL（构建时自动拷入）
├── assets/               图片与字体
├── config/settings.cfg   由根目录模板拷入；游戏实际读取这一份
└── saves/                权重存档
```

> 配置文件的真实位置是 `build/config/settings.cfg`。根目录的 `config/settings.cfg` 只是模板。
> `run.bat` 使用 `start` 启动，工作目录为 exe 所在目录，因此运行时相对路径一律相对 `build/`。

### 9.6 附：关键设计决策的依据

以下为开发过程中经过判断的技术决策，记录取舍依据。

**神经网络**

- **`softmax + 交叉熵` 的梯度化简为 `p − onehot`**：该形式正是策略梯度的 `∇log π(a|s)`，
  两个看似无关的推导在此处汇合——分类损失与策略梯度在实现上是同一个东西。
- **数值梯度检查选择中心差分**：截断误差为 `O(ε²)` 而非 `O(ε)`，
  在 `ε ≈ 1e-4` 附近可同时避开截断误差与浮点舍入误差。
- **累加式 `backward()` + 显式 `scaleGrad(1/N)`**：使批语义与学习率解耦，
  批大小变化时无需重新调整学习率。
- **初始化方式**：Xavier 按 `1/fan_in` 缩放以维持信号尺度，理由见 §3.1。

**强化学习**

- **REINFORCE 的梯度正比于 `p`**，且在 `p → 1` 时**恒等于零**——
  策略坍缩在数学上是不可逆的，这是策略梯度最需要防范的失败模式。
- **GAE 的 `λ` 在偏差与方差之间权衡**；critic 必须多跑几个 epoch，
  否则数千样本喂一次更新无法使价值函数收敛。
- **奖励设计**：不设存活奖励；差分式塑形项需额外补"原地位移"惩罚。
  理由见 §3.2 的"设计约束"。
- **自对弈使用冻结快照而非双方同时学习**：保持单轨迹假设成立，避免梯度方差翻倍。

**工程与协作**

- **用世界指纹为"缺乏语义保护的重构"上保险**：设计一个确定性、可复现、
  覆盖关键路径的哈希，使图形程序也能自动比对行为等价性。
- **把 1024 次逐格判断优化为 32 次解析计算**：凸区域可用半平面求交，
  并需处理直线近似平行于边的退化情况。
- **空间哈希的格子尺寸选择**：与碰撞半径、实体密度相关，过小会退化为全表扫描。
- **验证矩阵、唯一实现清单、最小判定实验**：三者共同构成 AI 协作的安全网，见第七节。
