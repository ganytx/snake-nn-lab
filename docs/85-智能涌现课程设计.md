# 智能涌现课程设计 — snake-nn-lab

> **状态：设计已定，A/B 步实施中。** 建立于 2026-09-24。
>
> **本文要解决的问题**：旧世界里"蛇会随机觅食 + 苟活到时间结束"。
> 负责人明确**不要这种蛇**。要的是在**新规则（食物圈）**下涌现出
> **跑图 / 占圈 / 合作 / 用饥饿淘汰对手**的蛇。
>
> 因此本文不是"修一个回归"，而是**设计一条能让智能涌现的课程**。

## 0. ★ 先钉死一个结论：合作在当前系统里【结构上不可观测】

这是 2026-09-24 排查出来的、**必须先解决**的事实。完整证据链：

| 环节 | 队友信息的命运 |
|---|---|
| `Perception.allies` | ✅ 算出来了（源码注释："合作的前提是知道队友在哪"） |
| `Perception.snakes`（含队友、带 `teamId`） | ✅ 算出来了 |
| `VisionGrid` 里的队友格子 | ✅ 标成了 `CELL_ALLY_HEAD` / `CELL_ALLY_BODY` |
| **`encoder.h`（32 维观测）** | ❌ **一个字节都没用** —— 入口只有 `p.self` / `p.grid` / `p.zones`，`p.snakes` 与 `p.allies` **从未被读取** |
| **`makeArenaConfig()` 训练配置** | ❌ **`allyVisibleCount = 0`**，训练时连算都不算 |
| **训练组队** | ❌ 3 条蛇 = **3 队各 1 条** → `teamId` 恒等于自己下标 → **队友数恒为 0** |

### 更严重的一条：队友在观测里被当成了【墙】

`VisionGrid.h` 的 `rayDistance()`：

```cpp
if (v & (CELL_WALL | CELL_ENEMY_BODY | CELL_ENEMY_HEAD |
         CELL_ALLY_BODY | CELL_SELF_BODY)) {    // ← 队友身体与墙同类
```

而实际上**队友之间可以互相穿过**（`friendlyFire = false`）。

> **后果**：AI 被喂了一个**错误的物理模型** —— 它以为旁边那堵"墙"会撞死它，
> 于是绕开；而那条"墙"其实是它能穿过去的队友。

### 结论

**"合作"不是"难学"，而是"不可观测"。** 无论训练多久、奖励怎么调，
一个看不到队友、又把队友当墙的网络，**不可能涌现出配合行为**。
这不是调参问题，是信息问题。

## 1. 推进顺序（按【依赖】排，不按优先级排）

```
A. 队友不再算障碍 + 队友进入观测      ← 合作的前提。不做它，后面全是空谈
        ↓
B. 训练时真正组队（同队 2 条蛇）      ← A 做完才有意义，否则队友数恒为 0
        ↓
C. 重构奖励尺度（觅食梯度 ≥ 躲避梯度）  ← A/B 会剧烈改变行为，观测先正确才好归因
        ↓
D. 加记忆（帧堆叠）                    ← 独立可插拔，最后一次性打开
```

## 2. A 步设计：队友可见

### 2.1 修掉"队友 = 墙"的错误物理模型

`rayDistance()` 增加一个**障碍掩码**参数，默认值 = 旧行为，保证
`RuleBrain`（规则 AI 躲障碍）**行为一字不变**。观测编码传
`BLOCK_MASK_NO_ALLY`（队友不算障碍）。

★ 这是正确的做法而不是"为了训练作弊"：**队友本来就能穿过**，
把它当障碍物是**观测在撒谎**。修正后观测与真实物理模型一致。

### 2.2 观测布局（32 → 35 维）

尾部追加 **3 维队友信息**，前面 32 维的语义和下标**完全不变**
（这样改动可核对、可对拍）。

| 下标 | 含义 | 编码 |
|------|------|------|
| 0..7 | 8 方向障碍距离 | `rayDistance(d, BLOCK_MASK_NO_ALLY)` ← **语义修正** |
| 8..15 | 8 扇区最近食物距离 | 不变 |
| 16 | 速度 | 不变 |
| 17 | 长度 | 不变 |
| 18..19 | 朝向 sin/cos | 不变 |
| 20..31 | 4 个食物圈 × 3 维 | 不变 |
| **32..34** | **★ 队友（新增）** | 见下 |

**新增 3 维的编码**（与圈的方位编码**同一套约定**，便于网络复用同一组特征）：

```
32  allyFwd   =  前向偏移 / ALLY_NORM      （+ = 队友在我前方）
33  allyRight =  右向偏移 / ALLY_NORM      （+ = 队友在我右侧）
34  allyCount =  min(1, 附近队友数 / 3)     （0 = 没有队友）
```

其中"前向/右向偏移"用**自身朝向的旋转坐标**（和圈的 `sin/cos(相对方位)`
表达的是同一件事），好处是"队友在我左前方"永远对应同一组数值，与绝对方位无关。

**新增常数（必须让负责人知晓）**：

| 常数 | 取值 | 依据 |
|---|---|---|
| `ALLY_NORM` | `1200.0f` | 直接照搬上面 `docs/70` 已定稿的 1200px 约定 |
| `ALLY_NEAR_COUNT` | `3.0` | 归一化除数：满编 3 条队友 → 1.0 |
| `ALLY_INFO_DIM` | `3` | |

**为什么用 3 维而不是 6 维**（"最近队友" + "最近敌人"各 3 维）：
维度越少越容易训。且**最近敌人可以从八方向障碍距离里读出来**
（敌方身体算障碍），所以不必重复编码。这没有牺牲可观测性，只是不重复。

**为什么只给"最近的一个队友"的方位**：`allies` 按距离排序，
最近的队友是合作/避让的主要对象。给全部队友会让维度线性增长，
而 3 条蛇的队形里"最近队友在哪"已经足够支撑基本配合（跟跑 / 包夹 / 让位）。

### 2.3 维度算式要重新表达（踩过越界写的坑）

现在是：

```cpp
constexpr int ZONE_OBS_SLOTS = (OBS_SIZE - 20) / 3;
static_assert(ZONE_OBS_SLOTS * 3 == OBS_SIZE - 20, ...);
```

字面量 `20` 和 `3` 是**魔法数**。新增队友块之后必须重新表达，
否则会重演 `devlogs/2026-09-23.md` 第 2 节那个**越界写 96 字节**的事故。

```cpp
constexpr int SELF_OBS_END   = 20;   // 自身状态结束
constexpr int ZONE_OBS_DIM   = 3;    // 每个圈占几维
constexpr int ALLY_INFO_DIM  = 3;    // ★ 新增：队友块占几维
constexpr int OBS_SIZE       = SELF_OBS_END + 4 * ZONE_OBS_DIM + ALLY_INFO_DIM;  // = 35

constexpr int ZONE_OBS_SLOTS = (OBS_SIZE - SELF_OBS_END - ALLY_INFO_DIM) / ZONE_OBS_DIM;
static_assert(ZONE_OBS_SLOTS * ZONE_OBS_DIM == OBS_SIZE - SELF_OBS_END - ALLY_INFO_DIM, ...);
static_assert(ZONE_OBS_SLOTS == 4, "食物圈任务用的是 4 个圈，观测必须刚好放下");
```

网络随之 `32 → [32] → 3` 变成 `35 → [32] → 3`：参数 **1155 → 1251**。

> ⚠️ **改 `encoder.h` = 所有已训练权重作废。** 这是预期内的 ——
> 现有权重本来就没学会（见 docs/30），不心疼。
> `weights/policy.txt` 与 `build/saves/` 会在加载时报"维度不匹配"，这是对的。

> ⚠️ **`replay_check` 的世界指纹会变**（因为 `rayDistance` 语义变了），
> 但 `replay_check` 比的是 **manual 与 arena 两份实现是否等价**，
> 与 `encoder.h` 无关 —— 所以它**应该仍然逐字节一致**。
> 这一点收尾时必须实跑确认。

## 3. B 步设计：训练时真正组队

### 3.1 现状（这是合作学不出来的直接原因）

```cpp
// TrainTask.h  makeArenaConfig()
if (total >= 9)      { teams = 3; perTeam = (total + 2) / 3; }
else if (total >= 3) { teams = total; perTeam = 1; }   // ← 3 条蛇 = 3 队各 1 条
```

3 条蛇 → `teamId` 恒等于自己下标 → **队友数恒为 0**。

于是 `docs/50` 写的"1 学 + 2 条规则 AI 陪练"，
**实际是 3 个敌对队伍**，不是 1 队 3 蛇。文档与实现不符。

### 3.2 修法：给 `TaskConfig` 加显式队伍表

```cpp
std::vector<AgentRole> roles = { AgentRole::Learner };
std::vector<int>       teams = { 0 };     // ★ 新增：与 roles 一一对应
```

**为什么用显式表而不是让 `makeArenaConfig` 去推导**：
"谁和谁一队"是**课程设计决策**，不是能从蛇数推导出来的东西。
上一版把"几条蛇"和"谁是学习的那条"分成两个信息源，已经吃过一次亏
（见 TrainTask.h 里 `roles` 取代 `snakes` 的说明）。同一个错误不该犯第二次。

`makeArenaConfig()` 改为按队伍表统计每队人数，不再自己算队形。

### ⚠️ 3.2.1 一个撞上的结构性约束：Arena 只支持**等长**队伍

`Arena::reset()` 建蛇是**等长矩形**：

```cpp
for (int t = 0; t < teamCount; ++t)          // 每队
    for (int k = 0; k < snakesPerTeam; ++k)  // 每条
→ 总蛇数 = teamCount × snakesPerTeam
```

所以「2 队但人数 2:1」这种**不等长队形建不出来**。

**第一版设计写的是 `teams = {0, 0, 1}`（3 条，2:1）—— 那是错的**：
Arena 会按 2×2 建出 **4 条**蛇，而 `roles` 只有 3 项
→ `EpisodeRunner`/`initialize` 读角色表时**越界**。
（这个错误是在写代码时核算出来的，没有进入编译。）

**最终采用等长的 2 队 × 2 蛇。**

### 3.3 食物圈任务的队伍结构（最终实现）

```
角色：{ Hunt,   Rule,   Rule,   Rule   }
队伍：{  0,      0,      1,      1     }
        └── 同队 ──┘     └── 同队 ──┘
        蛇0 = 学习中的网络（有 1 个队友）
        蛇1 = 规则队友
        蛇2/蛇3 = 对手（2 条，竞争压力真实）
```

- **蛇 0（学习）+ 蛇 1（规则队友）** 同队 → **这是"合作"得以存在的前提**
- **蛇 2/3（规则敌人）** 另一队 → 保留"躲避 + 猎杀"的学习信号
- `allyVisibleCount` 从写死的 **0** 改成按队表算出的 **1**

#### 代价（如实登记）

| # | 代价 | 说明 |
|---|---|---|
| ① | 学习内容变了 | 从「1 条 vs 2 个敌人」变成「1 条 + 1 队友 vs 2 个敌人」 |
| ② | 蛇数 3 → 4 | |

**食物不需要跟着重标定**（已核算）：`foodPerSecondOverride` 是**总速率**，
`makeArenaConfig` 把它摊成 `0.5 / 总蛇数`，而 `Arena` 每帧再乘回 `存活蛇数`：

```
4 条时 = (0.5/4) × 4 = 0.5 个/秒（总）
3 条时 = (0.5/3) × 3 = 0.5 个/秒（总）
```

总供给不变，只是**分食的蛇从 3 条变成 4 条**（每条 0.167 → 0.125 个/秒）——
稀缺度上升，这正是"占圈 / 抢食 / 淘汰"压力该有的样子。

**为什么不让队友也学习**：对手/队友行为固定，学到的策略才可归因。
如果队友也在变，分不清是"我方变强"还是"队友变强"。这一条沿用原设计。

## 4. C 步设计：奖励尺度重构（**待定，需负责人拍板**）

### 4.1 问题：觅食的梯度比躲避弱 60 倍

同一帧里，"做对事"和"做错事"的**信号强度完全不对等**：

| 信号 | 系数 | 每帧量级 |
|---|---|---|
| 靠近食物的塑形 `rZone` | `0.02 × Δd` | 直走 **+0.0083**（食物 900px 外时） |
| 存活 `rAlive` | `0.002` | **+0.002**（**不做任何事就有**） |
| 贴墙危险区 `rWallDanger` | `−0.5` | **−0.5**（做错就重罚） |

**"觅食"比"什么都不做"只多 0.0063/帧，而"贴墙"要罚 0.5/帧 —— 相差 79 倍。**

在这种奖励地形下，**策略坍缩成"原地绕圈"是正确解，不是 bug**：
绕圈稳定拿存活分，且所有塑形项在闭合回路上**净和恰好为 0**
（望远镜求和，见 docs/50 第 4 节），所以既不赚也不亏。

### 4.2 待定项（下一步与负责人逐条确认）

| 项 | 候选 |
|---|---|
| `rAlive` | 0（完全去掉） / 0.0002（降 10 倍） |
| `rZone` | 抬到与惩罚同量级（如 0.2） |
| `rWallDanger` / `rSnakeDanger` | 从 −0.5 降到 −0.05（保留"别贴"意图，不再压过觅食） |
| `rEat` | 是否随"食物稀缺度"重新标定 |

## 5. D 步设计：加记忆（待 C 步之后）

圈是「9 秒供食 + 5 秒空窗」轮流切换的 —— 这是**时间上的信息**，
而纯 MLP 既无记忆也无时钟。

**方案：帧堆叠**（stack frames）—— 把最近 K 帧观测拼接成输入。
保持"手写 MLP"的教学主线不变，是**纯输入层改动**，最容易验证。

| 常数 | 取值 | 依据 |
|---|---|---|
| `STACK_FRAMES` | 3（待确认） | 3 帧 ≈ 50ms，够表达"正在靠近/远离"的趋势；再多会让输入维度按 K 倍膨胀 |

`35 × 3 = 105` 维输入 → `105 × 32 + 32 + 32 × 3 + 3 = 3491` 参数，仍然很小。
