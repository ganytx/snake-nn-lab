### 步骤 D2 — 相机非法区间（缺陷 #15）

**现象**：`Camera::update()` 里
```cpp
m_center.x = Math::clamp(m_center.x, halfW, m_mapWidth - halfW);
```
地图是 20×20、视口是 1280×720 时，`halfW = 640 > mapWidth - halfW = -630`，
`clamp(v, 640, -630)` 的上下界反了 → 相机被钉在地图边界外的固定点。

**修法**：当地图某一轴**小于视口**时，该轴不再夹取，改为**居中显示整张图**。
两个轴独立判断，互不影响。

**验证方法**
1. `cmake --build build` 通过
2. 把 `config/settings.cfg` 的 `map_width` / `map_height` 改成 `20`，跑 `snake_game.exe`，
   确认**画面稳定显示地图中心、不抖动、不漂到地图外**
3. 改回 `2000`，确认大地图行为与改动前**完全一致**（这是主要回归点）

> ⚠️ 这一步需要你**用眼睛看一次** 20×20 的画面。我可以把两台配置都跑起来，
> 但「看起来对不对」需要你确认。

**回退**：`Camera.cpp` 单文件，改动约 6 行。

### 步骤 D3 — 小地图比例失真（缺陷 #26）

**现象**：地图是正方形（2000×2000），小地图控件是 180×120。
`Minimap` 构造函数里 `m_scaleX = displayW / mapW`、`m_scaleY = displayH / mapH`
**分轴独立缩放** → 横向被拉伸 1.5 倍。视野矩形、蛇的位置全部失真。

**两种修法，需要你选**（见文末决策点 ①）：

| | 修法 | 外观变化 |
|---|------|----------|
| **甲** | 控件本身改成正方形（`MINIMAP_WIDTH = MINIMAP_HEIGHT = 150`），单一缩放系数 | 右上角小地图变小、变方。**改动最干净** |
| **乙** | 控件保持 180×120 外框，内部画一个**居中的 120×120 正方形地图区** | 视觉尺寸基本不变，但地图四周有留白 |

**验证方法**
1. `cmake --build build` 通过
2. 跑 `snake_game.exe`，用 HUD 显示的玩家坐标 `X:/Y:` 核对：
   把蛇开到地图左下角，小地图上的点应当落在**正方形地图区的左下角**，
   而不是外框的左下角
3. 目视确认视野矩形是**正方形**（视口 1280×720 不是正方形，所以视野矩形本来就该是长方形；
   关键是它的**宽高比要等于 1280:720**，改动前是 1280:720×1.5）

**回退**：`Minimap.{h,cpp}` + `Constants.h` 三个文件。

### 步骤 D4 — 决策项：体节间距 20px vs 设计规范 12px（缺陷 #16）

**现状**：`Constants::SNAKE_SEGMENT_SPACING = 20.0f`，`GameConfig::segmentSpacing = 20.0f`，
而设计规范写的是 12px。

**技术上确认过的事实**（供你决策）：
- 改这个值**只影响外观**：体节更密（20→12 相当于体节数看起来多了 1.67 倍的密度）
- **不影响**吃食物长身体的速率（`addFoodEaten()` 是按「吃够 `foodSegments` 个 +1 节」计数，与间距无关）
- **不影响**碰撞判定（`CollisionSystem` 用的是体节的**世界坐标**，逐节检测，
  间距变小 = 判定点变密 → 蛇身判定**略微更实**，但不会穿透）
- 出生时铺轨迹的长度 `m_segmentCount × spacing × 1.2` 会同比缩短

**需要你决定**（见文末决策点 ②）：改成 12 / 保持 20 / 改成别的值。

### 步骤 D5 — 字体写死路径（缺陷 #14）

**现状**：`GameScene` 写死 `C:/Windows/Fonts/simhei.ttf` → `msyh.ttc` → `arial.ttf`。
换机器、换系统语言就可能全部失败，且**失败后没有任何提示**（`loadFromFile` 的返回值被忽略）。

**修法**：把字体文件**拷进 `assets/fonts/`**，优先从项目内加载，找不到再退回系统字体，
并**在加载失败时打一条明确的日志**（而不是静默地不显示文字）。

> ⚠️ 这一步需要**你提供字体文件**，或者在你的同意下我从 `C:/Windows/Fonts/` 拷一份
> `simhei.ttf` 进仓库。涉及字体授权，所以我不擅自做。

**验证方法**：把 `assets/fonts/` 临时改名，跑 `snake_game.exe`，
确认**有明确日志报错**且程序不崩；改回来确认中文正常显示。

## 2. 阶段 E — 加固

**目标**：把「会安静地浪费你一整晚」的隐患堵上。

### 步骤 E1 — 权重存取失败必须报警（本轮最重要的加固）

**现象**（实测复现过）：`nn::MLP::save()` 打不开文件时**只返回 `false`**，
而所有调用方**全部忽略了返回值**。后果是：权重没写进去，训练程序仍然照跑，
最后照样打印「权重已存到 xxx」——你会拿一个空文件去接游戏。

`load()` 同理：加载失败时静默保持随机权重，
`NeuralBrain` 只在 `displayName` 里标注「未找到权重, 随机」。

| 子步 | 内容 |
|------|------|
| E1a | `save()` / `load()` 增加**明确失败原因**（打不开文件 / 头部不匹配 / 数值个数不符），写进 stderr 或返回的错误串 |
| E1b | `train_probe` 检查返回值，失败就打印醒目错误并以**非零码退出** |
| E1c | `nn_selftest` 第 5 项**增加反向用例**：故意读一个不存在的文件和一个被损坏的文件，必须返回 `false` **且不污染参数**（要求 `worst == 0.0`） |
| E1d | `NeuralBrain` 加载失败时打印实际尝试过的路径 |

**验证方法**
1. ⚠️ **铁律**：改了 `src/nn/` 必须跑 `build\nn_selftest.exe`，**6 项全绿**
2. 把 `build\` 目录设为只读（或在 `train_probe` 里指定一个非法输出路径），
   确认程序**报错并以非零码退出**，而不是假装成功
3. 正常路径重跑，确认 `train_probe` 的基线数字仍是 **13.11 / 964.6 帧 / 40%**
   （这一项证明加固没有改变行为）

### 步骤 E2 — 观测编码收拢成真正的一份

**现象**：`CLAUDE.md` 的铁律说「训练和游戏必须共用 `src/rl/encoder.h` 里的同一个编码函数，
**只此一份**」。但事实上 `tools/train_probe.cpp` 里有一份**完整拷贝**的 `encode()`
（第 132~168 行），和 `rl::encodeObservation()` 内容目前一致 —— 也就是说，
**这条最重要的铁律现在是靠「两份代码碰巧一样」在维持的**。

这正是铁律警告的那类 bug 的温床：某天有人只改了 `encoder.h`，训练和游戏就开始各看各的世界，
而现象极具迷惑性（能跑、不报错、行为不对）。

| 子步 | 内容 |
|------|------|
| E2a | 让 `train_probe.cpp` **删掉自己的 `encode()`**，改调 `rl::encodeObservation()` |
| E2b | 加一个**编译期护栏**：在 `encoder.h` 里留一段注释说明「本函数是唯一实现，任何工具不得自带拷贝」，并在 `CLAUDE.md` 补一条核对方法 |
| E2c | 核对两份实现的**数值一致性**：改动前先跑一次 `train_probe` 记录基线，改动后必须**逐位复现** |

**验证方法**
1. `cmake --build build` 通过
2. `build\train_probe.exe` 的随机基线必须**仍是 3.79 / 360.2 帧 / 1.17 个 / 100%**，
   训练后**仍是 13.11 / 964.6 帧 / 3.44 个 / 40%**
   （能逐位复现 = 两份实现在数值上确实等价，这次收拢是纯粹的重构）
3. `grep -n "atan2(dr, dc)" tools/train_probe.cpp` → **0 命中**（拷贝已删除）

### 步骤 E3 — `rayDistance()` 死参数

**现象**：`VisionGrid::rayDistance(int dir, float cellSize)` 的 `cellSize` **完全没被用到**
（射线是逐格步进的，`maxSteps = VISION_COLS`）。留着一个不起作用的参数，
会让人误以为「改它能改射线精度」。

**修法**：删掉该参数，更新全部调用点。
**验证方法**：编译通过 + `train_probe` 数字不变（此改动**不应**影响任何行为）。

## 3. 阶段 A — 抽出无头 `Arena`

**目标**：让「训练用的世界」和「游戏里的世界」变成**同一份代码**。

### 为什么必须先做这一步

```
现状：  GameScene  ──► 世界（仿真逻辑写在场景里，场景需要窗口）
        train_probe ──► 另一个极简世界（自己写的，只有一条蛇）

问题：  训练学会的东西，和真实对局不是同一个世界。
        「练好了接进游戏就变傻」是迟早的事。
        而且想在训练里加对手、加队伍、加尸体机制，都得在第二个世界里重写一遍。
```

### 接口设计（关键是划清「谁负责什么」）

```cpp
namespace arena {

struct ArenaConfig {
    float mapWidth = 2000.0f, mapHeight = 2000.0f;
    int   teamCount = 1, snakesPerTeam = 1;
    int   playerTeam = -1;                  // -1 = 没有玩家

    // 蛇 / 食物 / 碰撞
    float snakeSpeed, snakeBoostSpeed, snakeTurnRate, segmentSpacing;
    int   snakeInitSegs, foodSegments, corpseSegments;
    float starvationTime, collisionForgive;

    // 食物生成
    int   foodMaxCount, foodSpawnCount, corpseScore;
    float foodSpawnInterval;

    // 感知
    float visionCellSize = 32.0f;
    int   allyVisibleCount = 2;

    bool  friendlyFire = false;

    // 每队用什么算法（对应 BrainRegistry 的 id）
    std::string teamBrains[8] = {"rule", ...};
};

class Arena {
public:
    Arena(const ArenaConfig& cfg, sf::RenderWindow* window);  // window 只给玩家输入换算用

    void reset();

    // 推进一个固定步长：移动 → 碰撞 → 饥饿 → 尸体 → 感知 → 决策 → 食物
    void step(float dt);

    // 只重建感知，不推进世界（训练/调试用）
    void refreshPerception();

    std::vector<agent::Agent>&       agents();
    const std::vector<agent::Agent>& agents() const;
    const arena::Perception&         perception(std::size_t i) const;
    FoodManager&                     food();
    const std::vector<Snake*>&       snakePtrs() const;

    float mapWidth() const;  float mapHeight() const;
    std::uint64_t tick() const;
};

}  // namespace arena
```

**Arena 负责**：agents（蛇身 + 大脑 + 感知缓冲）、FoodManager、CollisionSystem、
PerceptionBuilder、WorldView、出生布局、固定步长的 1~6 步。

**Arena 明确不负责**（本轮）：渲染、纹理、字体、相机、鼠标键盘、HUD、小地图、
观战切换、**限时与胜负结算**、队伍统计。

> 这几条「不负责」正是把 Arena 与「阶段 B（完整抽出）」区分开的边界。
> 以后要把结算搬进来，是**给 Arena 加方法**，而不是重构调用方 —— 接口按这个形状预留。

### 步骤 A5 — 新增 `tools/replay_check.cpp`「世界指纹」工具

**为什么要它**：`GameScene` 是图形程序，没法在无头环境里自动比对「改动前后世界是否一致」。
需要一个小工具，把同一局跑两遍、输出一个**确定性的世界指纹**。

```
输入：固定的 ArenaConfig + 固定 seed + 固定的动作序列（比如 RuleBrain 的决策）
输出：每 N 帧一行，含 tick / 每条蛇的 (x, y, angle, 长度, 分数, 存活) / 食物数
      最后一行是整局的哈希值
```

- 新增 CMake 目标 `replay_check`
- 用途：A2/A3 改完之后，**与改动前保存的指纹逐位对比**，证明「搬家没有改变行为」

**验证方法（A 线总验收）**
1. `cmake --build build` 五个目标全绿
2. `replay_check` 输出与**改动前保存的指纹完全一致**（这是「搬家不改行为」的唯一硬证据）
3. `snake_game.exe` 手动跑一局：3 队对抗、观战、小地图、结算**全部正常**

### 决策点 ② 的补充分析：体节间距到底该不该改

我查过全部引用点，事实是：

| 影响面 | 结论 |
|--------|------|
| 外观 | **变**。20→12 视觉上体节密 1.67 倍，蛇看起来更「粗壮」 |
| 生长速度 | **不变**。`addFoodEaten()` 按个数计数，与间距无关 |
| 碰撞判定 | **几乎不变**。判定点更密 → 蛇身判定略微更实，不会穿透 |
| 出生铺轨 | **变短**。`m_segmentCount × spacing × 1.2` 同比缩短 |
| 已训练权重 | **不受影响**。观测编码里没有「体节间距」这一项 |

所以它**纯粹是手感/观感决策**，不影响学习。你说了算。
