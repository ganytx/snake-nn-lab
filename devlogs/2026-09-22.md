### 0.2 发现的问题：`nn_selftest` 报「5 项通过，1 项失败」

第一次跑自检时 `[5/6] 权重存 / 取 往返一致性` 是**失败**的，
但打印的「存取后输出最大差异 = 0.00e+00」。

**根因不在代码**：当时代理运行在**只读沙箱**里，`save()` 打不开文件、返回 `false`，
于是第 5 项判 `saved && loaded && worst == 0.0` 为假。而 `worst` 之所以是 0，
是因为写入失败后 `load()` 也失败、`b` 保持初值，两边恰好都是未训练的网络。
取得写权限后该项恢复通过。

**但这个现象本身暴露了一个真问题**（后来由 E1 处理）：
`save()` / `load()` 只返回 `bool`，而**所有调用方都忽略了返回值**。
权重没写进去时程序照跑、照样打印「权重已存到 xxx」，
这正是那种「安静地浪费一整晚」的 bug。

### 0.3 发现的问题：文档里的「无头」说法不准确

`CLAUDE.md` 与 `docs/30` 都写「`src/brain/` 与 `src/rl/` 禁止 include 任何 SFML 头文件」，
但 `src/entities/Snake.h` 第 3 行就是 `#include <SFML/Graphics.hpp>`，
而 `train_probe` 为了构造 `Snake` 必须链 SFML（`CMakeLists.txt` 第 83 行）。

**所以本项目里「无头」的准确含义是「不创建窗口、不加载资源」，而不是「不依赖 SFML」。**
这一条已在 `docs/60` 里写清，并把「彻底剥离 SFML」登记为后续独立任务。

#### D1c 删除 `AIController`（缺陷 #24）

替换为 `RuleBrain` —— 对局里**真正在用**的算法。

**为什么必须替换而不是简单删掉**：`bench_sim` 的「AI 决策」环节原本量的是
`AIController::decideAngle()`。那是一个**已经不参与任何对局的旧实现**，
量出来的「AI 决策成本」没有意义。

**顺带修掉的一处测量错误**：原 `bench_sim` 的帧循环顺序是
`移动 → AI 决策 → 感知填充`。而 `RuleBrain` 只吃 `Perception`，
放在感知之前决策就等于让它看上一帧的（第一帧则是空的）感知。
所以顺序必须改成 **`感知填充 → AI 决策 → 移动`**。

**另一处处理**：原来有个「AI 每帧都决策（不节流）」的上界档，靠传 `aiDt = 1.0`
来强行越过 `AIController` 的反应时间。`RuleBrain` 的 `think()` 内部自己按
`m_reactionTime` 节流，没有「外部传 dt 越过去」这个入口了。

处理方式：把 `RuleBrain::decide()` 从 `private` 提到 `public`，
上界档直接调 `decide()` 绕过节流 —— 语义比原来更准确：
**实际对局中大脑每帧都被调用（只是内部会跳过决策），
所以这一档量的是「如果每帧都真的重算一次」的成本上界。**

- 删除 `src/systems/AIController.{h,cpp}`（共 272 行）
- `CMakeLists.txt`：`bench_sim` 的 `AIController.cpp` 换成 `brain/RuleBrain.cpp`
- `bench_sim.cpp`：`brains` 从 `std::vector<AIController>` 改成
  `std::vector<std::unique_ptr<arena::Brain>>`，
  每条蛇用 `onEpisodeStart(1000 + i*97)` 给不同种子
  （否则所有蛇抽到同一个反应时间、同一条漫游轨迹，测量会偏）

## 2. 阶段 D（续）— D2 相机非法区间、D3 小地图比例

### D2 相机非法区间（缺陷 #15）

**修法**：`Camera::update()` 里两个轴**分别判断**，且先判断"地图比视口还小"：

```cpp
m_center.x = (m_mapWidth <= m_viewWidth)
           ? m_mapWidth * 0.5f                                  // 装不下 → 居中
           : Math::clamp(m_center.x, halfW, m_mapWidth - halfW);
```

**根因**：地图 20×20、视口 1280×720 时 `halfW = 640 > mapWidth - halfW = -630` ——
夹取区间下界比上界还大，`clamp` 的结果被钉死在 640，相机跑到地图外。

**这个缺陷是真实可达的**：`SettingsScene.cpp` 第 29~30 行给地图宽高的输入范围是
**`20 ~ 20000`**，用户真的可以把地图调到 20。

**验证**：把地图临时改成 20×20 跑了一次游戏并截图，画面**稳定、地图居中**，
HUD 计时正常倒数（1:59 → 1:55）。对比修复前画面会被钉死在左上角，
「地图正中出现一坨蛇」这个画面本身就证明修复生效。

### D3 小地图比例失真（缺陷 #26）

**修法**（按负责人决策「甲」）：

- `Constants::MINIMAP_WIDTH/HEIGHT` → **150×150**（原来 180×120，横向拉伸 1.5×）
- `Minimap` 把 `m_scaleX` / `m_scaleY` 合并成**唯一的 `m_scale`**，
  取 `min(displayW/mapW, displayH/mapH)`（等比装得下）
- 新增 `m_offsetX/Y` 做居中留白，新增 `worldToWidget()` 统一换算
- 视野矩形宽高也用**同一个** `m_scale`，否则框会被拉成和地图不一样的变形
- 地图尺寸变化时自动重算（`recomputeScale()`）

**验证**：`train_probe` 基线（3.79 / 13.11）与标墙对拍（400 例 × 409600 格）
均不变 —— 这是数值回归；**视觉效果待负责人确认**（原因见第 3 节）。

## 5. N1~N4 修复（负责人决定全修）
### N1 配置落盘路径 —— CMake 拷贝 + 按优先级定位

**先确认了根因**：`run.bat` 写的是
`start "" "%BUILD_DIR%\snake_game.exe"`，而 **`start` 会把子进程的工作目录设成
exe 所在目录** → 游戏实际在 `build\` 下运行 → 读写的是 `build\config\settings.cfg`。
根目录那份 `config/settings.cfg` 从来没被读过，也从来没被写过。
`CMakeLists.txt` 里**没有任何一步把 `config\` 拷进 `build\`**，所以这个耦合一直没暴露。

**修法**：

1. `CMakeLists.txt` 给 `snake_game` 加 POST_BUILD：把根的 `config/settings.cfg`
   拷到 `$<TARGET_FILE_DIR:snake_game>/config/settings.cfg`
2. `Game.cpp` 新增 `findConfigDir()`：按优先级找配置目录
   （exe 旁边 → 上一级 → 当前工作目录），**读写都用同一个结果**
3. `saveConfig()` 写不进去时**打印错误**（以前是静默 return，
   界面还提示"保存成功"，磁盘上什么都没发生）

**踩到的坑**：配置文件里原先是中文注释，CMake 拷贝时会**重新编码**，
拷过去的中文全变成乱码，还把换行吞掉、下一行粘到了 `#` 后面。
→ 配置文件里的注释改成**纯 ASCII**。这个坑值得记：**被工具链拷贝的文件不要放中文注释**。

### N2 `teamBrains` 不落盘 —— 配置读写改成表驱动

根因不只是"漏了一个字段"，而是**两串手工维护的 if/else 和 `file <<`**：

```cpp
loadConfig()  : 22 个 else if (key == "...")     // 手工维护 A
saveConfig()  : 22 行 file << "..."              // 手工维护 B
```

A 和 B 必须同步，而实际上没有（`teamBrains` 两边都没提）。这条防线已经失效了。

**修法**：抽 `src/core/GameConfigFields.h` —— 一张 X-macro 表，
展开三次分别生成「结构体成员 / 读配置分支 / 写配置语句」。

```cpp
#define GAME_CONFIG_FIELDS(X_FLOAT, X_INT, X_BOOL)  \
    X_FLOAT(mapWidth,  map_width,  2000.0f)         \
    X_INT  (teamCount, team_count,        3)        \
    ...
```

**加一个新配置项 = 加一行**，三处同时就有了。

> ⚠️ **这个文件故意不加 `#pragma once`**：同一份 `.cpp` 里要展开它好几次，
> 加了 include guard 第二次就被整段跳过。
> 症状是 `GAME_CONFIG_FIELDS was not declared in this scope` 加一片
> `xxx was not declared in this scope`。**这个坑真的踩了一次**，编译报错贴出来才发现。
>
> ⚠️ 宏里的注释必须用 `//`：反斜杠续行的宏在预处理器眼里是**一整行**，
> `/* */` 会把后面的内容一起注释掉。

### N3 三个死 AI 配置项

`aiInitCount` / `aiMaxCount` / `aiSpawnInterval` 全项目**零引用**，
却仍在设置界面显示、可调、无效果。从 `Game.h` 和 `SettingsScene` 删除。

### N4 参数缺少有效下界

**两层防护**：

1. 设置界面抬下限：地图 `20 → 400`、`foodSpawnCount` `0 → 1`、
   `foodSpawnInterval` `0.0 → 0.1`
2. 新增 `GameConfig::sanitize()` —— **与界面无关**的兜底，
   在 `loadConfig()` 末尾、`GameScene` 构造和重开时都会调用

为什么两层都要：手改配置文件可以**绕过界面的 min/max**。
不兜底的话，`map_width=20` 会造出一个"看起来在跑、其实什么都不会发生"的世界 ——
蛇一出生就撞墙，而且食物生成范围 `[20, mapW-20]` 直接变成负数。

## 6. 食物圈玩法设计（负责人提出）

**负责人的判断**：*「蛇想要躲避很容易，捕猎很难」* ——
饥饿是**唯一可以被别人剥夺**的死法，所以「占领食物、饿死对手」是唯一可行的间接攻击路线。
当前"全图随机撒食物"让这条路走不通。

**规则**：4 个固定圈，固定顺序循环，每 10 秒在一个圈内生成「蛇总数」个食物；
旧食物不清除但加超时；把 4 个圈的距离与方位加进观测。

设计稿见 [docs/70-食物圈玩法设计.md](../docs/70-食物圈玩法设计.md)。

**我提出的关键技术点**：

> **网络是纯 MLP，没有时钟也没有记忆。** 所以"固定顺序"这个**时间上的信息**
> 如果不进观测，网络就无法知道"现在该去哪个圈"——两轮的观测可能完全一样。
>
> 解法：对 4 个圈各给 `sin(方位)`、`cos(方位)`、`距离` 共 12 维。
> **正在供食的那个圈食物最多，所以"食物数/距离"本身就编码了"轮到谁了"**，
> 不需要时钟。代价是 `OBS_SIZE` 20 → 32，参数 771 → 1155。

**另一个必须提的风险**：`train_probe` 里的 `struct World` 是**另一份世界实现**。
圈逻辑如果在 `GameScene` 和它里面各写一遍，两份很容易不一致 ——
而"两个世界不一致"会导致"学不会"的原因无法定位。
所以设计稿里建议**先抽 `Arena` 再实现食物圈**。

## 7. E2 观测编码收拢 —— 挖出一个真正的 bug

### 起因

`tools/train_probe.cpp` 里有一份**完整的 encode() 拷贝**，和 `src/rl/encoder.h`
的 `rl::encodeObservation()` 看起来一模一样。也就是说铁律

> 「训练和游戏必须共用同一个编码函数，**只此一份**」

实际上一直是靠"两份代码碰巧一样"在维持的。

收拢之后训练结果从 `13.11 / 吃 3.44` 变成 `12.28 / 吃 0.12`。我不肯接受这个差异，
写了个同进程对拍：把旧拷贝原样放回来，同一个 `Perception` 喂给两个函数。

### 对拍结果：**两份并不等价**

**240 万次比对，最大差异 0.96**（观测取值 0~1，所以这是巨大的差）。

差异全部落在**扇区边界格**上 —— 正前 / 正后 / 正左 / 正右，以及四条正对角线。

给 `encoder.h` 的循环装探针后，原因一目了然：

```
[NEW] r= 0 c=16  ang=-1.5707963267948966  t8=2                    sector=2
[OLD] r= 0 c=16  ang=-1.5707963267948966  t8=1.999999999999998  sector=1

[NEW] r=14 c=14  ang=-2.3561944901923448  t8=1                    sector=1
[OLD] r=14 c=14  ang=-2.3561944901923448  t8=0.999999999999997  sector=0
```

**`ang` 完全相同**，但 `t8` 差在第 15 位，`static_cast<int>` 截断后差 1。

根因：那句话

```cpp
sector = static_cast<int>(((atan2(dr,dc) + π) / (2π)) * 8.0) % 8;
```

在角平分线上的格子里会算出「差 1 个 ulp 的整数」。而且**结果取决于表达式的书写顺序**
—— `(ang+P)/(2P)*8` 与 `8*(ang+P)/(2P)` 经编译器重结合后末位不同。

**结论：扇区边界格的归属，是由浮点末位舍入决定的。这个分类方式本身就是脆弱的。**

### 修法：改成纯整数比较

```cpp
inline int foodSector(int dr, int dc) noexcept {
    if (dc > 0) {                                    // 右半平面
        if (dr < 0) return (-dr > dc) ? 3 : 2;       // 右上；正对角线归 2
        if (dr > 0) return ( dr > dc) ? 4 : 5;       // 右下；正对角线归 5
        return 5;                                    // 正右
    }
    if (dc < 0) {                                    // 左半平面
        if (dr < 0) return (-dr > -dc) ? 1 : 0;      // 左上；正对角线归 0
        if (dr > 0) return ( dr > -dc) ? 6 : 7;      // 左下；正对角线归 7
        return 7;                                    // 正左
    }
    return (dr < 0) ? 0 : 4;                         // dc == 0：正前 / 正后
}
```

结果**完全确定**：与浮点无关、与编译器无关、与优化等级无关。

> 写第一版时我把 8 个扇区**整体错位了 1**（上/右/下/左的映射写反）。
> 对拍立刻暴露了 —— 所有维度都差，而不是只有边界格。
> **这就是对拍的价值：错的版本会以完全不同的方式失败。**

### 中途的一个假警报（教训）

改完之后有一次跑出「平均只吃 0.12 个」，看起来很像"编码改坏了，网络退化成苟活"。
我差点就按这个结论去深挖。

**实际原因**：那次跑的时候我的对拍探针还挂在 `encoder.h` 里（带 printf 的循环）。
清理干净后重跑 3 次，**三次结果完全相同**：

| | 平均回报 | 平均存活 | 平均吃 | 死亡率 |
|---|---|---|---|---|
| 随机基线 | 3.79 | 360.2 帧 | 1.17 个 | 100% |
| **统一编码后（新）** | **16.52** | **1200 帧** | **3.87 个** | **0%** |
| 旧基线（`docs/50` 记录） | 13.11 | 964.6 帧 | 3.44 个 | 40% |

**新编码反而更好**：回报 +26%，吃食 +12.5%，死亡率 40% → 0%。

> **一条纪律**：**带调试探针的二进制，跑出来的数字不能当结论。**
> 我看到 0.12 时的第一反应应该是"先确认这个二进制是干净的"，
> 而不是"先假设编码改坏了"。

## 15. ★ 查出并修掉一个严重的越界写（本轮最难）

### 症状

`train_probe` 跑完第 0 个训练回合后崩溃（`0xC0000005`），
而且**崩在 `Arena::reset()` 函数入口与第一条 printf 之间** —— 连函数体都没进去。
随机策略基线跑 200 局却完全正常。

我一开始怀疑自己刚抽的 `rl::Trainer`，查了很多轮没找到，
中途还用 shell 正则误伤过两次源码（已全部修回）。
**这个判断是错的** —— 根因在一个和 Trainer 无关的地方。

### 根因

`src/rl/encoder.h`：

```cpp
constexpr int MAX_ZONES = 8;
for (int i = 0; i < MAX_ZONES; ++i) {      // ← 错在这里
    const int base = 20 + i * 3;
    if (i < n) { obs[base+0..2] = ...; }
    else       { obs[base+0..2] = 0,0,1; } // ← 无条件执行
}
```

观测尾部只有 `obs[20..31]` 共 **12 个槽**，每圈 3 维 → **只放得下 4 个圈**。
`i=4..7` 时写到 `obs[32..43]` —— **越界 12 个 double = 96 字节**，
而且 `else` 分支无条件执行 → **每次感知都必踩一次**。

### 为什么时序这么诡异

越界写的是调用方**栈上保存的 XMM 寄存器**（Win64 下 XMM6–XMM15 是**非易失**的）。
写坏它不改变返回值、不立刻报错，只在"保存→恢复"的接缝处才露出来：

- 基线 200 局 + 训练第 0 局：被踩的 96 字节恰好属于没人再读的位置 → 一切照跑
- 某个回合开始：被踩的位置变成返回地址 → `reset()` 一进去就崩

**"越界"和"第几局崩"本来就没有因果关系** —— 这就是它难查的全部原因。

### ⚠️ 游戏本体也在踩

`NeuralBrain::think()` 用的是同一个函数、同样持有 `double obs[rl::OBS_SIZE]`
—— **游戏里每条神经网络蛇每帧都在踩自己 96 字节栈**。

修一个头文件同时修好三处（`train_probe` / `NeuralBrain` / `EpisodeRunner`）。

### 修法

```cpp
// 观测向量里放得下几个圈（≠ 世界能建几个圈）
constexpr int ZONE_OBS_SLOTS = (OBS_SIZE - 20) / 3;
static_assert(ZONE_OBS_SLOTS * 3 == OBS_SIZE - 20, "圈观测必须刚好填满尾部");
for (int i = 0; i < ZONE_OBS_SLOTS; ++i) { ... }
```

`MAX_ZONES`（世界最多几个圈）与 `ZONE_OBS_SLOTS`（观测里放得下几个圈）
是**两个不同的概念**，混用就出事。

**已有权重不作废**：网络输入向来只读 `obs[0..31]`，
越界那 12 个 double 从未进入 `toInput()`。

### 验证（全部实测通过）

| 验证项 | 结果 |
|---|---|
| `train_probe` 退出码 | ✅ **0**（之前 -1073741819） |
| `nn_selftest` | ✅ 6 项全过 |
| `bench_sim` 标墙对拍 | ✅ 400 例全一致 |
| `replay_check manual/arena` | ✅ 逐字节一致（哈希 `a09974567ce40005`） |
| 游戏内训练模式 | ✅ 正常运行 15 秒无崩溃，界面正常 |

### 方法上的收获

这个 bug 是靠**反汇编**定位的：解 `train_probe.cpp.obj` 的 COFF 符号表 +
`.pdata`/`.xdata` 得到栈帧布局（`sub rsp,0x1D0`），定位到 `stepObs` 占
`[rsp+0x90, rsp+0x190)`，而**偏移 256 处正好是保存的 XMM6/7/8** ——
与越界的 96 字节完全对上。

> **教训**：遇到"函数入口就崩、连第一条语句都执行不到"，
> 不要怀疑逻辑 —— 那是**栈被写坏**的特征，要去找越界写。

| 随机基线 | 3.23 | 350.4 帧 | 0.69 个 |
| 训练后贪心 | **0.12** | **12.0 帧** | 0.00 个 |

**比随机还差。** 根因：视野固定 1024px、地图 4000×4000 → 蛇看不见圈在哪 →
食物只在 4 个圈里 → 奖励信号极稀疏 → REINFORCE 学不动。

我在设计时就把"观测里要能看出轮到哪个圈"写进了方案（12 维），
但那是给"已经知道要去圈里"的策略用的；**怎么让它先发现圈，是课程设计问题**。

### 踩到的四个坑（都很典型）

1. **`replay_check` 里一行硬编的 `5`**
   `Snake::applyConfig(..., 5, 2)` 的 `foodNeeded` 漏改成 1。
   症状：两边位置、得分**完全相同**，只有体节数不同，指纹从第一行分叉 ——
   看起来像"世界推进逻辑不等价"。
   最后靠打印「每次进食前后的体节数」才定位：
   ```
   manual: segs 12->12   ← 吃 5 个才长一节
   arena : segs 12->13   ← 吃 1 个就长一节
   ```

2. **初始食物撒放时机影响随机序列**
   `Arena` 构造里会建 N 个 `RuleBrain`。让调用方"构造后再撒食物"，
   `rand()` 序列就错位了。做成 `ArenaConfig::initialFoodCount`，
   把时机固定在"撒食物 → 建蛇"，两边才一致。

3. **`printf` 格式串与实参类型不匹配**
   我写的格式串里 `%d` 少了一个、实参却给了 4 个 → 打印出 `inf` / `nan`。
   看起来像"训练数值爆了"，实际数据完全正常（`sumR=12.2, deaths=1`）。
   **教训：看到 inf/nan 先确认打印本身对不对，再去查数值。**
   我在上面浪费了好几轮。

4. **`registerBuiltinBrains()` 忘了调 —— 同一个坑踩了两次**
   第一次是 `arena` 模式，第二次是新增的 `zones` 模式。
   症状都是 `0xC0000005` 访问冲突、**一句提示都没有**。
   最后把它移到 `main()` 里只调一次。

### 一条流程教训

这四件里有三件（`5`、撒放时机、`printf`）**都不是逻辑错误，而是配置/打印错误**，
但现象都伪装成"核心逻辑坏了"。我每次都先去怀疑逻辑，绕了很久。
**下次遇到"两边不一致"，先逐项核对两边的【配置值】，再怀疑逻辑。**
