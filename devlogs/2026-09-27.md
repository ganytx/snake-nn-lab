## 2. 三层配置（这是本轮的结构性改动）

负责人把两个设置页的职责划清之后，配置自然分成三层。**这三层的边界是本轮最重要的设计决定**：

```
① 通用世界规则   → GameConfig 的标量字段（速度/转向/间距/饥饿/碰撞/尸体…）
                   只在【主菜单 → 设置】里改
② 每模式默认值   → GameConfig::ModeConfig modes[3]
                   （队数/每条/算法/每队权重/食物速率），也在大设置里改，可 SAVE
③ 这一局的配置   → Game::m_matchCfg，开局时从 ①② 拷一份
                   只在【模式选择页 → 设置】里改，不存盘
```

**为什么必须分三层**：如果小设置直接改 ②，那"只影响这一局"就不成立 ——
下次进同一模式会带上上次的临时改动。而如果 GameScene 读 ①，
小设置改的东西就完全不起作用（**而且不会报错，只表现为"改了没用"**）。

★ 判据（写进了代码注释）：**`GameScene` 里凡是读配置，一律 `getMatchConfig()`。**
这一条是用 grep 验证的，不是靠记忆。

## 3. 三个模式的定义（唯一实现：`src/core/GameModes.{h,cpp}`）

| | 模式 1「随机食物圈」 | 模式 2「无限模式」 | 模式 3「大混战」 |
|---|---|---|---|
| 地图 | 3000² | 3000² | 3000² |
| 队伍 | 3 队 × 3 条 = 9 | **5 队 × 1 条 = 5，没有组队** | 5 队 × 3 条 = 15 |
| 算法 | nn / nn / rule | 全 nn（每队 1 条 → 每条蛇一个算法） | 全 nn |
| 食物 | 圈内产；供食期瞬时 2 个/秒 | 全图随机；每蛇 1/9 每秒 | **极少**：全图每秒 1 个 + 尸体 |
| 结束 | 限时 / 只剩一队 | **永不结束**，玩家死了转观战 | 限时 / 只剩一队 |
| 特殊 | 圈位置每轮随机 | 每 20 秒加一条（上限 20），新生蛇随机挑存档 | 靠击杀尸体维生 |

### ★ 关于「食物速率」的口径（我错了一次，记下来）

我一开始以为 `foodPerSecond` 是"每个圈"的速率，负责人直接纠正：

> 「？？每时每刻只有一个活跃圈产食物啊？你是什么意思？」

核实 `FoodManager::update`：

```cpp
if (m_foodPerSecond > 0.0f && m_sched.spawning(m_zoneTimer)) {  // ← 只在供食期
    m_spawnAccum += m_foodPerSecond * dt;                       // ← 这是【总】速率
    const int active = m_sched.activeZone(...);                 // ← 只往活跃圈放
```

所以：**`foodPerSecond` 是世界总速率，而且只在供食期产**。
而 `Arena::step` 里它 = `foodPerSnakePerSecond × max(存活数, 1)`。
于是"三队三蛇总共 2 个/秒" = `foodPerSnake = 2/9`。

★ 教训：**讨论速率时先把"分子分母"写出来再算。**

## 4. 每队可加载不同权重（负责人要求）

原来的 `NeuralBrain::setPendingWeights` 是**全局**的，一次 reset 只能表达
"所有网络队用同一个文件"。而负责人要"不同队伍加载不同权重"，所以：

- `ArenaConfig` 新增 `teamWeights[MAX_TEAMS]`
- `Arena` 造每一队的脑**之前**设 `setPendingWeights`、**造完立刻清空**

⚠️ "造完立刻清空"这一条是必须的 —— 忘了清就会让之后每个 `NeuralBrain`
都去读那一份（**这正是缺陷 #43 的形态**）。

## 5. `Arena::addAgent()` —— 途中踩到一个「会静默崩」的坑

无限模式要"中途加蛇"，而 Arena 原来只能 `reset()` 时一次性建好全部蛇。

**★ 坑在这里**：`m_ptrs` 里存的是 `&a.body` —— **指向 vector 元素的裸指针**。
如果 `m_agents.emplace_back()` 触发扩容，整个 vector 搬到新内存，
**那些指针全部变成悬垂指针**，而碰撞系统与感知都拿它当有效值用。

原来的代码是安全的（"只在全部建完后填一次指针"，之后再不增删）。
**是我加的 `addAgent()` 打破了这个前提。**

修法：`reset()` 里 `m_agents.reserve(32)`。上限 32 的依据：三个模式规模是
9 / 20 / 15，留了余量。以后要更大的规模必须同步改这里。

**同一个坑的另一面**：`GameScene` 里缓存的 `m_humanBrain` 裸指针也会失效。
虽然 Arena 内部 reserve 之后不会真的失效，但那是 Arena 的实现细节 ——
`GameScene` 依赖它就把两个类的内部假设绑死了。所以改成
**每次按索引现查**（`humanBrain()`，一次 dynamic_cast，一帧一次可忽略）。

★ 教训：**往 vector 里加元素之前，先问"有没有人存了我的元素地址"。**

## 7. 途中发现的两个缺陷

### #50 `SettingsScene` 的"退出不保存"

旧版的做法是"临时副本 + 保存时拷回"：

```cpp
m_tempConfig = m_game->getConfig();   // 拷贝一份
auto& cfg = m_tempConfig;             // 改的是副本
...
L129:  m_game->popScene();   // BACK 按钮：不保存直接返回
L153:  m_game->popScene();   // ESC     ：返回，不保存
```

而 `doSave()` 只在按 SAVE / Ctrl+S 时调。**所以改动被静默丢弃**，
界面上没有任何提示 —— 这正是本项目最怕的"设了没用还不报错"。

⚠️ 负责人说这个 bug 早就修好了，本轮只是**重写设置页时确保不再犯**。
重写后的语义：**编辑即时生效**（改的是真配置）+ ESC 返回自动写盘；
"放弃改动"由 R 提供 —— 比"忘了按保存就白改"清楚。

### #51 `GameScene::fixedUpdate` 里有一段重复的相机代码

观战/跟随两套分支**逐字写了两遍**（是两次编辑叠加留下的）。
判据：同一段逻辑出现两次时，改一处忘一处会表现成
"观战镜头有时能动、有时不能"，很难查。

## 10. 编译错误的教训（本轮前 6 次都是"标识符归属"问题）

| 报错 | 性质 |
|---|---|
| `'NeuralBrain' has not been declared` | 漏 include |
| `'teamCount' was not declared` | 删字段漏改一处（而且是**死函数**在报错） |
| `'foodPerSnake' has no member` | 字段搬进 ModeConfig 了，写入方没跟着改 |
| `invalid use of incomplete type` | **前向声明写在了 `namespace game` 里面** → 声明出了一个完全不同的 `game::GameConfig` |
| `'m_learnerAct' was not declared` | 加探针时只加了使用、没加声明 |
| `'NeuralBrain' does not name a type` | **`rl/` 层里 `dynamic_cast` 了 `brain/` 的类型 → 违反分层铁律** |

★ 共同点：**全是"标识符的归属/可见性"问题，不是逻辑问题。**
这类错误编译器一次只报一个（或一批同源的），要多轮才能清干净。

★ 其中最值得记的是最后一条：那段"队友一致性探针"是给一个**我已经放弃的
问题**加的诊断代码，而它从写下的那一刻起就**违反分层**（`rl/` 不能依赖
`brain/`）—— 我当时只想着"诊断用 dynamic_cast 最省事"。
**教训：诊断代码同样受分层约束，因为它在同一个 .cpp 里被编译。**

### 13.1 `#57` 的细节：为什么"速率"不能代替"上限"

这是本批最值得记下来的一条。食物的**场上存量**本来就由两个数决定：

```
稳态存量 = 生成速率 × 食物寿命
```

要"食物管够"就得提高速率，但速率是按**存活蛇数**缩放的
（`食物/秒 = 每蛇速率 × 存活数`，见 `Arena::step`）。
如果把速率提到"看起来源源不断"，存量就会跟着失控：
40 个/秒 × 30 秒寿命 = **稳态 1200 个**。
1200 个食物铺在 3000² 上已经不是"管够"，而是"地图变红" ——
蛇根本吃不完，于是"觅食"再次退化成"随便走都能撞到"。

**所以"速率"和"上限"是两件事，必须分开：**

- 速率决定"被吃空之后多久补回来" → 给足（看起来源源不断）
- 上限决定"地图上同时有多少" → 卡死（能看清、也吃得完）

实现落在 `FoodManager::update()` 的生成分支里，两个容易写错的地方：

1. **到了上限也必须把累加器减掉**。写成"满了就跳过整个 while"的话，
   `m_spawnAccum` 会在满的时候一路涨到几百；之后只要被吃掉一个，
   就会**瞬间补上一大片**。
2. **尸体不占这个上限**。尸体是别的蛇死了留下的战利品，
   而大混战的核心食物来源就是尸体 —— 让自然生成的上限把它挤掉，那个模式就没玩法了。
   所以计数器只数普通食物（`m_foodCount`），尸体不参与。

计数器用**每帧重算**而不是"生成 +1 / 被吃 −1"：
增量维护要在六条路径上（圈内生成、全图生成、定点生成、种子撒、被吃、寿命到期）
各写对一次，漏一处就是"上限永远不生效"或"上限提前生效"的静默 bug。
反正每帧本来就要遍历一遍统计圈内数量，顺手多数一个计数器不会更慢。

### 14.1 编译错误：`const` 引用上做写操作

```
GameScene.cpp:178:68: error: no match for 'operator='
  (operand types are 'const std::string' and 'std::string')
  178 |   mc.teamWeights[t] = m_spawnWeights[pick(m_spawnRng)];
```

**根因**：`rebuildArena()` 里那行引用是
`const GameConfig::ModeConfig& mc = cfg.modes[...]` ——
它在"只读配置"的年代写的。我新增的"开局随机挑权重"要**写**它，就崩了。

**★ 这个错误真正浪费时间的不是修，而是定位**：
报错位置在 L178，而"病根"是 L66 的一个 `const`。中间隔了 100 多行，
报错信息也完全没提 `const` 引用（它只说 `const std::string` 不能赋值）。

**修法不只是去掉 `const`** —— 这一步还有个**顺序陷阱**：
随机挑出来的权重必须写进 `mc.teamWeights`，而它之后才被拷进 `ac.teamWeights`
（`Arena` 只认 `ac` 里那份）。原来的位置在拷贝循环**之后**，
去掉 `const` 也**照样不生效**（而且不报错）。
所以把整段随机逻辑**上移**到拷贝循环之前，并在两处都写了"位置有讲究"。

> **教训**：给一段只读代码加写操作时，要同时检查
> ① 那个引用是不是 `const` ② 写进去的东西**后来有没有被人读走**。
> 两个都不会报错，一个是编译错误（好查），一个是静默失效（难查）。

## 15. 编译（负责人跑的第二遍）：编码错误 `#60`

### 15.1 现象

```
Error copying file (if different) from
  ".../snake-nn-lab/saves/鍙︿竴绉?txt"
  to ".../snake-nn-lab/build/saves/".
mingw32-make[2]: *** [CMakeFiles\snake_game.dir\build.make:536: snake_game.exe] Error 1
mingw32-make[2]: *** Deleting file 'snake_game.exe'
```

> 注意最后两行：make 把**已经生成好的 exe 删掉了**。
> 也就是说这一个 POST_BUILD 步骤失败，代价是"整个游戏都没了"，
> 而不是"只是没拷存档"。这解释了为什么它比看上去严重。

### 15.2 根因：cmake 跑在 GBK 代码页下

`另一种.txt` 在 UTF-8 里是 9 个字节；本机的 `cmake.exe` 生成
`build.make` 时按 **GBK** 解释/写出这些路径，于是：

```
另一种.txt   ->   鍙︿竴绉?txt
```

那个 `?` 是关键证据：**有字节映射不回目标字符集**，转换是**有损**的。
所以这不是"显示乱码"，而是**写进 Makefile 的路径本身就是错的**，
make 去拷贝一个不存在的文件，当然失败。

**★ 这和我上一轮修 `#58`（`build\saves\` 没被同步）是同一个坑的两层：**

| 层 | 问题 | 后果 |
|---|---|---|
| 运行时 | `ckpt::kDir = "saves"` 是相对路径，游戏在 `build\` 下跑 | 3 份存档游戏看不见（#58） |
| 构建期 | 中文文件名进了 Makefile 命令行 | **编译直接失败**（#60） |

而**为什么存档名是中文**：那是负责人自己命名的（`喜欢转.txt`、`略显智能.txt`），
名字本身就是有用的信息（记录那份权重的行为特征）。不该为了迁就工具改名。

### 15.3 修法：让 PowerShell 枚举目录，而不是让 CMake 拼路径

```cmake
add_custom_command(TARGET snake_game POST_BUILD
    COMMAND powershell -NoProfile -ExecutionPolicy Bypass
            -File "${CMAKE_SOURCE_DIR}/tools/sync_saves.ps1"
            -SourceDir "${CMAKE_SOURCE_DIR}/saves"
            -DestDir "$<TARGET_FILE_DIR:snake_game>/saves"
)
```

CMake 命令行里现在**只剩纯 ASCII 的脚本路径**，中文名全程不经过任何代码页。

`tools/sync_saves.ps1` 里：
- 用 `Get-ChildItem -LiteralPath <源目录> -Filter *.txt -File` **从文件系统读真实目录项**
  （`-LiteralPath` 是必须的：`-Path` 会把 `[` `]` 之类当通配符）
- 排除 `auto_latest.txt` 与 `enemy_snapshot.txt`（负责人的要求）
- **只拷不删** —— 训练器写在 `build\saves\` 的自动产物不受影响

### 15.4 ★ 教训：这个脚本自己也必须纯 ASCII

写完之后我检查了一遍，发现脚本的**注释里**有 33 个非 ASCII 字节
（我把乱码示例 `鍙︿竴绉?txt` 抄进去了）。这本身就是个雷：

> **Windows PowerShell 5.1 把没有 BOM 的 `.ps1` 文件按 ANSI（本机 = GBK）读取。**
> 也就是说 UTF-8 的中文注释会被同样地搞坏 —— **和 15.2 是同一类 bug，只是又上了一层。**

所以：脚本内**一个非 ASCII 字节都不能有**（已改成 0，用字节扫描核对过），
所有中文说明搬到 `CMakeLists.txt`（cmake 按 UTF-8 读它，没问题）。
存档的**中文文件名**照旧 —— 它们只在运行时从文件系统读，从不写进任何脚本。

> **通用规则（值得记进 CLAUDE.md 那一类）**：
> 在代码页不是 UTF-8 的机器上，**非 ASCII 字符串只能出现在
> "确定按 UTF-8 读取"的文件里**（源码、UTF-8 的 cmake 脚本），
> 绝不能出现在：命令行参数、Makefile 内容、无 BOM 的 `.ps1`/`.bat`。

## 17. 负责人第四批：随机圈的距离/种子 + 无限模式的存活上限

三条问题，其中**两条是我的真 bug**，一条是"刻意的行为被当成了 bug"。

### 17.1 随机圈：种子"固定"是刻意的，但**每局都一样**是错的

位置用的是 `(cycle, posSeed)` 的**确定性哈希**，`posSeed = 20260924` 写死。
确定性本身是铁律（`replay_check` 的世界指纹要靠它），
但**游戏里也该每局不同** —— 负责人连开两局看到同一串圈位，那是真的像坏了。

修法：`ZoneLayout` 新增 `posSeedOffset`，`GameScene` 每局用 `std::clock()` 填。

> ⚠️ **不能用 `rand()` 取这个偏移**。`rand()` 是全局序列，
> 而 `Arena::reset()` 里的出生点、食物位置都从它抽 —— 在 reset 之前调它
> 会让世界序列整体错位，`replay_check` 的哈希立刻对不上。
> 时钟不碰全局序列，是纯表现层差异。

偏移 0（默认）= 完全可复现，`replay_check` 用它自己的固定配置，不受影响。

### 17.2 随机圈：距离上限缩短

负责人："只把距离上限缩再短一些吧。"

| | 旧 | 新 |
|---|---|---|
| 区间（短边比例） | 0.40 ~ 0.60 | **0.20 ~ 0.30** |
| 3000² 上的实际距离 | 1200 ~ 1800px | **600 ~ 900px** |
| 按 250px/s 跑 | 4.8 ~ 7.2 秒 | **2.4 ~ 3.6 秒** |
| 一轮供食期 | 9 秒 | 9 秒 |

**为什么下限也跟着降**：只降上限会把区间压成 `1200 ~ 900`（上限比下限还小），
而代码里 `dHi = max(dLo, min(dMax, saneMax))` 会把它俩拉平 →
**每一轮距离完全一样**，比原来更糟。所以区间整体平移，
保持 1.5 : 1 的跨度比例不变。

新距离下，蛇跑到下一个圈还剩 5 秒以上能吃东西 ——
而旧值下"跑到就该换圈了"，那条永远在赶路的蛇其实是被距离坑死的。

### 17.3 无限模式：`#62` 尸体占着上限

```cpp
const int total = static_cast<int>(m_arena.agents().size());  // ← 含尸体
if (total >= m_spawnMaxTotal) return;
```

死蛇**一直留在 `agents` 里**（Arena 从不删），所以累计生过 20 条之后
`total >= 20` 永久成立 → **世界再也不出新蛇**。

★ **训练侧早就写对了**：`TrainTask` 里有一句注释
"死掉的蛇不再重生，否则 20 条蛇的上限永远达不到" ——
**游戏侧漏了同一件事**。这类"训练对了、游戏漏了"的分歧是本项目的老毛病，
根源是两边各写了一遍"死亡之后怎么办"。

修法三条：
1. `Arena::removeDeadAgents()` —— 死蛇从场上移除
2. 生蛇改为"**存活数 < 8 时每 2 秒补一条**"（不再是"每 7 秒无条件加"）
3. 另设**累计生成 20 条**的硬上限

### 17.4 `removeDeadAgents()` 为什么必须由 Arena 提供

`m_agents` 一改，**三样东西同时失效，而且都不会报错**：

| 容器 | 为什么失效 |
|---|---|
| `m_ptrs` | 存的是 `&agent.body` 裸指针，下标一变就指错蛇 |
| `m_deathCauses` | 与 agents **下标一一对应** |
| `m_humanIndex` | 玩家那条的下标 |

三个都是 Arena 的私有状态，只有 Arena 自己能一致地修好。
调用方拿到的应该是一个**已经自洽的世界**。

两个实现细节值得记：

- **压缩必须同步**：只 `resize` 前者会让死因表整体错位 →
  `train_probe` 的死因统计悄悄变成假的（不报错）。
- **`m_humanIndex` 用"重新数一遍"而不是"按下标推算"**：
  推算要维护"它前面死了几条"的平移关系，容易写错；
  而 `Snake::isPlayer()` 是蛇自己的属性，与下标无关。
  **用不可能错的做法**。

### 17.5 ★ 一个顺序陷阱：玩家死了要先切观战，再清场

新增的 `removeDeadAgents()` 会把玩家那条蛇也删掉 → `humanIndex()` 变成 -1。
而 `checkSpectatorSwitch()` 里 `hi < 0` 是**直接 return** 的
（它把"没有玩家"当成"纯 AI 对局"）。

所以如果先清场再判断，**玩家死了永远不会切到观战**，
相机会卡在最后一帧不动 —— 现象是"我死了，画面定住了"。

正确的顺序（`fixedUpdate` 里）：

```
step() → checkSpectatorSwitch() → removeDeadAgents() → updateSpawning()
```

- `checkSpectatorSwitch` 必须在 `removeDeadAgents` **之前**（否则 humanIndex 已 -1）
- `removeDeadAgents` 必须在 `step` **之后**（它会重建 `m_ptrs`，而 step 全程依赖它）
- `removeDeadAgents` 必须在 `updateSpawning` **之前**（生蛇上限判的是场上蛇数）

同理，排行榜那句"你已阵亡，观战中"的判据也从
"humanIndex 那条还活着吗"改成了 `m_spectator` —— 否则那句话**永远显示不出来**。

### 17.6 关于"死蛇移除"的取舍（如实记下）

负责人选的是**死蛇从场上移除**。代价：

- 排行榜只剩活蛇，看不到"已阵亡"的行（但那个模式永不结束，死蛇只是噪声）
- 玩家那条死了就消失，观战只能看别人
- 模式 1/3 **不做移除**：那两个模式靠"只剩一队"分胜负，
  而"某队全灭"需要那条蛇留在场上被 `winningTeam()` 统计到
  （删尸体不改变"哪队活着"，但没必要为模式 2 的需求去动另外两个模式的结算）

## 18. 编译（负责人跑的第三遍）：`Agent() = delete` 与 `resize`

### 18.1 错误

```
stl_construct.h:119: error: use of deleted function 'agent::Agent::Agent()'
   required from 'std::vector<Agent>::resize(size_type)'
   required from Arena.cpp:420
```

### 18.2 根因：缩容也要"可默认构造"

我写的是：

```cpp
m_agents.resize(k);        // k < size()，本意是"只保留前 k 个"
m_deathCauses.resize(k);
```

而 `agent::Agent` 的默认构造函数是 **`= delete`** 的
（`Snake` 没有默认构造，必须给出生参数 —— 见 `Agent.h:40`）。

**★ 关键点：`vector::resize(k)` 在 k < size() 时也要求元素可默认构造。**
直觉上"缩容嘛，删掉尾巴就行了"，但标准把 `resize` 定义成
"append 或 erase 到 n 个元素"，实例化时会走 `_M_default_append` 那条路径，
于是 `Agent()` 被引用 → 编译期报错。

改用 `erase()`：它只做移动赋值 + 析构，**不要求默认构造**。

```cpp
m_agents.erase(m_agents.begin() + k, m_agents.end());
m_deathCauses.erase(m_deathCauses.begin() + k, m_deathCauses.end());
```

### 18.3 ★ 这个错误为什么"看起来在别处"

报错栈是 `stl_construct.h` → `stl_uninitialized.h` → `vector.tcc` → `Arena.cpp:420`。
**四层模板展开**，最后才指到我的那一行，而且信息里完全没有
"你不该用 resize" 这层意思 —— 它只说 "use of deleted function Agent()"，
看起来像"Agent 定义有问题"，而不像"我调用方式有问题"。

> **教训**：`std::vector<T>` 只有
> `T` 可默认构造时才能用 `resize(n)` / `resize(n, v)` 扩容。
> 对"必须带参数构造"的类型（`Agent`、`std::thread`、某些 RAII 包装），
> 一律用 `reserve` + `emplace_back` 增长、用 `erase` 收缩。
> **这个项目的 `Agent` 正属于后者**，值得记在 `Agent.h` 旁边。

### 18.4 顺带排查

按同一类风险扫了一遍全项目的 `.resize(`：

| 位置 | 容器 | 结论 |
|---|---|---|
| `Arena.cpp` | `std::vector<agent::Agent>` | ★ 就是这次报错的，已改 erase |
| `Arena.cpp:655` | `std::vector<bool> aliveBefore` | ✅ 用 `reserve` + `push_back`，正确 |
| `TrainingTeamScene.cpp:45/134` | `std::vector<std::string>` | ✅ string 可默认构造，合法 |

## 19. 负责人第五批：无限模式"不会生成新蛇" + 主菜单动效背景

### 19.1 `#66` "卡在下一条蛇：3s，不会生成新的蛇"

**★ 先说清楚：我无法复现**（编译不了）。所以这一节分两部分：
能确定的（读代码就能证明的）和推断的。

#### 能确定的 ①：新蛇**会**一出生就撞死，而且死得无声无息

`Arena::addAgent()` 原来只有一行随机撒点。而蛇出生时身体会沿
**朝向的反方向铺 `snakeInitSegs × segmentSpacing × 1.2 = 288px`**
（见 `Snake::prefillTrail`）。

于是落点只要离某条蛇近一点，就等于**把一条 288px 长的身体横穿到别人身上**：

- 要么它自己的头立刻撞上别人的身体
- 要么别人一头撞在它身上

两种都是 1 秒内就死。而 `removeDeadAgents()` 会把尸体**立刻**删掉
→ **画面上完全看不出发生过什么**。

这完全解释了"倒计时在走，但永远不出现新蛇"。

**修法**：出生点改成"64 次试探，挑离所有现存蛇最远的那个"，
安全距离取 `蛇身全长 + 60px`；实在挤不下时（20 条蛇挤在一起）
再扫 12 个朝向，选一个"身体铺开方向最空"的。

> ★ 这里有个刻意的取舍：**宁可挤一点也不要"找不到就不生成"**。
> 因为"不生成"的表现恰好就是负责人报的那个现象 ——
> 那会让一个偶发问题看起来像永久卡死。

#### 能确定的 ②：倒计时读数**每 1 秒才跳一次**

```cpp
static_cast<int>(m_spawnIntervalSec - m_spawnTimer + 1.0f)
```

它把浮点**截断**成整数。2 秒的间隔下读数是这样跳的：

| 计时器 | 显示 |
|---|---|
| 0.0 ~ 1.0 | 3 |
| 1.0 ~ 2.0 | 2 |

也就是**每个读数会停整整 1 秒**。一个卡了 1 秒的整数读数，
和"真的卡住"在肉眼上分不出来 —— 负责人看到的"卡在 3s"很可能就是它。

**修法**：改成保留一位小数、显示"剩余时间"：
`2.0 → 1.5 → 1.0 → 0.5 → 生成`，一眼能确认它在走。

#### 能确定的 ③：`#65` 计时器会被"存活数反复穿越"清零

原来"存活数 ≥ 目标 → `m_spawnTimer = 0`"。而存活数在 8 附近是**反复穿越**的：

```
死一条 → 7 → 补一条 → 8 → 又死 → 7 → ...
```

每次穿越都把计时器清零 → **永远攒不够 2 秒** → 补蛇次数远少于预期。

**修法**：不清零，改成**封顶**（满员时最多攒到 `m_spawnIntervalSec`）。
效果是"满员期间停在 1 条待发，一旦掉到 8 以下最多 2 秒补上" ——
既不会空转，也不会因为攒了几十秒而瞬间刷一堆。

> 这是"计时器"和"节拍器"的区别。我们要的是**节拍器**：
> 它只回答"距上次补蛇过了多久"，不回答"世界现在缺不缺蛇"。

#### 推断的部分：诚实地说明

上面三条能解释"看不见新蛇"，但**我无法证明**负责人那一次就是这三条之一。
所以这轮**加了 F3 调试面板**，把这条链上的原始值摊出来：

```
--- spawn ---
timer 1.37 / 2
spawned 9 / 20
targetAlive 8

```

## 21. `#68` 无限模式生蛇：我把语义整个理解反了

### 21.1 负责人的纠正

### 21.2 正确的语义：两个数各管一件事

| 数 | 管什么 |

存活 < 8   → 每 2 秒补一条（快）
8 ~ 20     → 每 7 秒补一条（常规）
存活 = 20  → 停手

世界会一路涨到 20 条并稳定在那儿。8 从来不是终点。

## 22. ★★★ 修掉「假圈」：位置随机模式下开局凭空吃掉一个圈（负责人报的缺陷）

### 22.1 负责人报的现象（原话大意）

> 正常应该是：出现一个活跃圈 → 产一段时间食物 → 下一个食物圈选好 →
> 一段时间 → 活跃圈关闭 → 一段时间 → 下一个食物圈变活跃，开始产食物。
> 然而现状是：出现一个活跃圈产食物，产一段时间食物，下一个食物圈出现（**假圈！！**），
> 活跃圈关闭，**又选了一个新的位置作为活跃圈**。那个假圈从始至终未产生食物。

### 22.2 ★ 为什么这次没有靠读代码猜，而是先做工具

读代码时我两次得出"这段是对的"的结论：

- `Arena::step` 第 0 步的 `swap + relocateRandom` —— 逻辑自洽
- `activeZone()` 与 `spawning()` 的轮次算法 —— 在 t=cycleDuration 处同时切换，也自洽

**"自洽"和"画面正确"是两件事。** 这个项目已经因为"读了代码觉得没问题"栽过多次，
所以这次先补工具：给 `replay_check` 加了一个模式

```
replay_check.exe randomzones      （简写 rz）
```

它逐秒打出：轮次 / 活跃下标 / 是否在供食 / **两个圈的坐标** / **每个圈实际的食物数**。

判据写在输出里：*空窗期被预告的"下一个圈"坐标，应当在下一轮变成活跃圈，
且它的食物数开始上涨。若活跃坐标换成了别处 = 假圈缺陷。*

> ⚠️ 原来只有 `zones` 模式，而它用的是**固定四方位**圈 —— 测不到"位置随机"这条路径。
> 而"位置随机"恰恰是唯一会**搬动圈心**的模式，缺陷只可能在这里出现。

### 22.3 工具第一次跑就抓到了

```
 初始圈数 = 2
   槽位 0: (659, 757) 半径 150.0      ← reset() 选好的活跃圈
   槽位 1: (571,1367) 半径 150.0

 秒  轮次 活跃        槽位0 (x,y)            食物
  1    0    0     (   571,  1367)      0     ← 第 1 帧就变了！(659,757) 不见了
  2    0    0     (   571,  1367)      1
```

**`(659, 757)` 在第 1 帧被丢弃，从始至终没产过一个食物 —— 那就是负责人看到的"假圈"。**

### 22.4 根因：`m_posCycle = -1` 让开局多做了一次轮换

```cpp
// reset():
m_posCycle = -1;                    // ← "第 0 轮还没处理"
m_food.setZones(build(...));        // ← 已经给两个槽位都挑好坐标了

// Arena::step() 第 0 步，第一帧：
const int cycle = int(zoneTimer / cycleDuration());   // t=0 ⇒ cycle = 0
if (cycle != m_posCycle) {                            // 0 != −1 ⇒ 成立！
    std::swap(zones[0], zones[1]);                    // 把预备位提到活跃位
    relocateRandom(zones[1], ...);                    // 预备位换到新坐标
    m_posCycle = cycle;
}
```

**时间还是 0、第 0 轮一秒都没跑，就做了一次完整轮换。**

| | 想要的 | 实际的 |
|---|---|---|
| 第 0 轮活跃圈 | `(659,757)`（`build()` 选的） | `(571,1367)` |
| `(659,757)` 的命运 | 供食 9 秒 | **被丢弃，0 食物** |

后面第 1→2→3→4 轮的换轮**诊断显示完全正确**（预告的圈都变成了活跃圈并产食物）。
**所以是"开局凭空吃掉一个圈"，不是每轮都错。**
这解释了为什么现象是"**一次**假圈"而不是"每轮都有假圈"。

### 22.5 修法（一行）

```cpp
m_posCycle = 0;   // 原来是 -1
```

`build()` 在 t=0 就已经把第 0 轮布置好了、**不需要再换一次**。
设成 0 之后，第 0 轮整轮都用 `build()` 选的位置供食，第 1 轮起才走 `swap + relocateRandom`。

**重开一局仍然安全**：`m_posCycle = 0` 是每局 `reset()` 都设的，
所以新一局照样重新开始，不会残留上一局的 cycle 号。

### 23.1 负责人这次的描述（关键，直接指向了根因）

> 我已经重复很多很多遍了，根本不是你说的那回事！！！
> 不是「0~8s 一个亮圈在 A → 9~13s 两个圈 → 14s B 变亮、A 消失」这样！
> 而是「**A 亮 → A 亮，出现了个 B 不亮 → A 不亮，突然出现一个全新的 C 在亮，
> 而 B 始终不亮**」！

**"B 始终不亮"这一句是决定性的。** 它把问题从"视觉呈现"变成了
"**预告的那个圈永远不会变成活跃圈**" —— 也就是一个纯粹的世界状态错误。

### 23.2 我前面两次为什么没找到

| 次数 | 我的结论 | 为什么不够 |
|---|---|---|
| 第 1 次 | 修 `m_posCycle = -1` → `0`（开局多做一次轮换） | **那个缺陷是真的**（`build()` 选好的圈在第 1 帧被丢弃），但它只解释"**一次**假圈"，不解释"**每轮**都有" |
| 第 2 次 | 以为是渲染规则（供食期只画活跃圈） | 猜的，没有数据支撑。负责人当场否掉 |

**教训：同一个现象可以有多个根因，修好一个不等于修好了现象。**
而我第 2 次已经退化成"猜一个最像的原因"，那是这个项目最忌讳的做法。

### 23.3 逐帧数据（`replay_check randomzones` + `SNAKE_ZONE_DEBUG=1`）

```
[BEFORE]  cycle=1 m_posCycle=0  槽0(659,757)  槽1(571,1367)
[SWAPPED]                       槽0(571,1367) 槽1(659,757)   ← swap 本身完全正确
[AFTER]                         槽0(571,1367) 槽1(530,915)   ← relocate 只改了槽1
         活跃=1  ← 但活跃下标指向【槽1】，也就是那个全新的圈 C
```

**`swap` 和 `relocate` 都是对的。错的是"活跃下标指向哪个槽位"。**

### 23.4 根因：两个互相矛盾的约定

| | 约定 | 谁定的 |
|---|---|---|
| **活跃下标** `ZoneSchedule::activeZone(t,n) = cycle % n` | **槽位固定轮转**：轮 0 用槽 0、轮 1 用槽 1、轮 2 用槽 0 …… | 食物生成 / 感知 / 渲染都用它 |
| **`std::swap` 的做法** | 每轮把"预告的那个"换到槽 0 ⇒ **活跃圈永远在槽 0** | 原来那段轮换代码 |

**这两个约定不可能同时成立。**

到奇数轮时 `cycle % 2 = 1` 指向**槽 1** ——
而槽 1 恰好是刚 `relocateRandom` 出来的**"下一个圈"**。于是：

- 槽 0 里那个**预告的圈**：**永远不会被点亮，也永远不产食物** ← 负责人看到的 B
- 槽 1 里那个**全新的圈**：被点亮、并且真的产食物 ← 负责人看到的 C

**与负责人的描述一字不差。**

### 23.5 修法（负责人选的"甲"）：去掉 `swap`，改为"重挑下一轮要用的槽位"

```cpp
const int curSlot  = ((cycle)     % n + n) % n;   // 本轮的活跃槽（build/上一轮已选好）
const int nextSlot = ((cycle + 1) % n + n) % n;   // 下一轮要用的槽 —— 现在选好即"预告"
m_cfg.zoneLayout.relocateRandom(zones[nextSlot], W, H, cycle + 1,
                                zones[curSlot].x, zones[curSlot].y);
```

**`cycle % n` 这个下标算法一行都没改**（食物生成/感知/渲染都依赖它），
只是不再 swap ⇒「预告的圈」与「下一个活跃圈」**必然是同一个槽位**。

**配套改动（必须有，否则第 1 轮的预告仍然不算数）**：
`ZoneLayout::build()` 里给槽位 `i` 用的随机数从 `cycle = i` 改成 **`cycle = i + 1`**。

> ★ 为什么：位置必须**提前一轮**选好，而"第 k 轮的圈位置"统一用 `pickRandomCenter(cycle = k)`。
> 槽位 `i` 是第 `i` 轮要用的圈 ⇒ 它该用 `cycle = i + 1`（在 `build` 里相对 `i` 而言）。
> 这样"`build()` 给的初始位置"和"第 0 轮时预告的位置"算的是**同一个坐标**。

## 25. ★★★ 位置随机圈：最终正确的结构（负责人两次纠正后定稿）

### 25.1 负责人的要求（原话，就两句）

> 食物圈轮换，**每次随机选择一个圈**，预告圈和活跃圈**必须是相同的圈**，
> 这么简单的逻辑，很困难吗？

### 25.2 最终结构（一句话）

> **第 k 轮开始时，只挑【第 k+1 轮】的位置；活跃圈一动不动。**

于是两条要求同时成立：

| 要求 | 怎么满足的 |
|---|---|
| 每次随机选一个圈 | 每轮都在挑一个新位置，它在**下一轮**生效 |
| 预告圈 = 活跃圈 | 预告用的槽位 = 下一轮的活跃槽位，**同一个坐标**（用同一个 cycle 号选） |
| （附带）没有瞬移 | 活跃圈整轮不动，换轮只是"原来那个淡色的圈变亮了" |

### 25.3 为什么"活跃圈提前一轮定好"是关键

位置必须**提前一期**选好，否则"预告"这件事不成立：

```
第 k 轮开始时：
  ① 活跃圈【不动】        ← 它的位置是第 k−1 轮就预告好的
  ② 重挑【下一轮】的槽位   ← 这就是新预告，也是第 k+1 轮的活跃圈
```

**如果反过来**（第 k 轮开始时重挑本轮活跃圈的位置），就会把
上一轮预告的位置**当场覆盖掉** —— 预告圈永远没机会变成活跃圈。

### 25.4 ★ 我这一轮连着犯的三个错（都值得记）

#### 错误 1：让槽位永不变身份 → 圈被"钉死"

我为了满足"预告圈 = 活跃圈"，改成"不 swap、只重挑下一轮的槽位"，
同时让 `zones[0]` **永远**是当前活跃圈。

- **语义上**每轮确实选了新坐标（`zones[0]` 每轮都被重挑）
- **但它坐在哪个槽位上永远不变** ⇒ 位置一换，玩家看到的还是"那两个圈"

负责人一眼看出来：**"食物圈只有两个，也不轮换，很多局都固定那两个同样的位置"**。

> ★ 教训：**"槽位固定轮转"是下标算法（`activeZone(t,n) = cycle % n`）定的，
> 不能靠 swap 去改变它。** 我想用"活跃圈永远在槽位 0"去讨好预告逻辑，
> 结果和下标算法打架 —— 这正是上一节 `#70` 的同一个矛盾，我又踩了一次。

#### 错误 2：在换轮时重挑"本轮活跃圈"的位置 → 预告圈被覆盖

修错误 1 时我加了"每轮给当前活跃槽位挑新位置"，想表达"每轮随机换位置"。
结果是**它把上一轮预告的坐标当场覆盖**，预告圈依然永远不变亮。

逐帧数据（`replay_check randomzones`）直接抓到了：

```
帧841  轮1  活跃圈(571,1367)   ← 还是预告的位置
帧842  轮1  活跃圈(231,1124)   ★变了！  ← 被重挑掉了
```

#### 错误 3：`build()` 里改随机数 cycle 号

为配合错误 1 的方案，我把 `build()` 里槽位 `i` 的随机数从 `cycle = i`
改成了 `cycle = i + 1`，导致第 1 轮用了一个和 0 轮预告不一样的位置。

**修法：`build()` 在位置随机模式下【不再挑位置】**，只把槽位搭出来
（边建边挑会读到还没 push 的 `zones[0]`，顺序一错就崩）。
位置统一由 `Arena::applyConfigToSystems()` 在开局显式布置：

```cpp
pickRandomCenter(zs[0], ..., /*cycle=*/0, cx, cy);              // 第 0 轮活跃圈
relocateRandom  (zs[1], ..., /*cycle=*/1, zs[0].x, zs[0].y);    // 第 1 轮 = 第 0 轮的预告
m_posCycle = 0;
```

### 25.7 ★ 这一轮真正的教训

**我把一个"两句话就能说清"的需求，用三轮改动做成了一团。**

根子上是我**没有先把不变量写下来**。这个功能其实只有两条不变量：

```
不变量 A：预告的那个圈，下一轮必须变成活跃圈（同一个槽位、同一个坐标）
不变量 B：每一轮的活跃圈位置都必须是新的（不能钉死）
```

**A 和 B 完全不冲突** —— 只要位置**提前一轮**定好，两条同时成立。
我却先按 A 做（牺牲了 B），再按 B 补救（破坏了 A），来回三轮。

> ★ **正确的做法**：动手前先把不变量列出来，再找一个同时满足它们的结构。
> 这次我是在负责人的第二次纠正之后才这么做的 —— 而那时已经浪费了三轮。

## 26. ★★ 预告圈的【出现时机】：供食还剩 3s 时才出现（负责人定稿）

### 26.1 负责人的规格（原话）

> 不要一开始就有预告圈，预告圈是在活跃圈产食物**还剩 3s** 后出现的，
> 然后中间有一定时间 gap，然后再被激活。

### 26.2 时间线（默认：供食 9s + 空窗 5s + 预告提前 3s）

```
 0s ───────────── 6s ────────── 9s ───────── 14s ────────── 23s
 │←── 只有活跃圈 ──→│←──── 预告期 ────→│←─ 空窗 ─→│← 新活跃圈供食 ─→
 │    在产食物      │    还在产食物     │  都不产   │
                     ↑
              预告圈在这里出现
              （spawnDuration − previewLead = 9 − 3 = 6s）
```

预告圈从出现到被激活共 `previewLead + gapDuration` = **8 秒**，
而圈间距 600~900px 按 250px/s 要跑 2.4~3.6 秒 —— **留了充足余量**。

### 26.3 实现：`previewing` 是新的判据，唯一实现在 `ZoneSchedule`

```cpp
float previewLeadSeconds = 3.0f;      // 新增字段

bool previewing(float t) const {      // 唯一实现
    float local = t − floor(t/c)*c;
    return local >= (spawnDuration − previewLeadSeconds);
}
```

| 层 | 改动 |
|---|---|
| `ZoneSchedule` | 新增 `previewLeadSeconds` + `previewing()` |
| `PerceptionConfig`（WorldView） | 新增 `zonePreviewing` 字段 |
| `Arena::step` | `m_view.zonePreviewing = m_sched.previewing(...)` |
| `PerceptionBuilder` | `v.visible = v.active \|\| world.zonePreviewing` |
| `GameScene` / `LiveTrainingScene` / `Minimap` | 画不画"下一个圈"改用 `previewing` |

> ⚠️ **`|| v.active` 不能省**：少了它，供食期前 6 秒连**当前圈**都会被藏掉，
> AI 就彻底看不到食物圈了。活跃圈必须永远可见。

### 26.4 ★ 验证时踩的两个读数陷阱（都值得记）

#### 陷阱 1：`runner.lastObservation()` 是【死前那一帧】的冻结值

第一次验证时我用了 `runner.lastObservation()` —— 那是**学习那条蛇最后一次决策**
的观测。而那条蛇常常几秒就撞死，它一死 `runner.decide()` 就不再被调用，
那份观测**冻结在死前那一帧**。于是整个采样窗口读到的都是同一个哨兵值，
看起来像"可见性改动没生效"。

**修法：自己跑 `PerceptionBuilder::build(view, ...)` + `encodeObservation`，
拿到的才是"此时此刻这个世界会喂给网络什么"。**
为此给 `Arena` 加了一个只读访问器 `view()`。

#### 陷阱 2：`build()` 在蛇死时**连圈都不填**

改完陷阱 1 之后仍然读到空圈。打印内部状态才发现 `percep.zones.size() == 0`
而 `arena.food().zones().size() == 2` —— 根因是：

```cpp
if (!self.isAlive()) { out.self.alive = false; return; }   // ← 这里
```

**蛇一死就 return，连"圈是全局信息"都不填了。**
（那个 `return` 上面的注释自己还写着"即使提前返回，食物圈也要填" ——
注释和代码是矛盾的，属于已知小瑕疵。）

**修法：采样时现场挑一条【活着的】蛇**，而不是固定用 0 号。

> ★ **教训**：验证"世界会给网络喂什么"时，**读数的来源必须是当前世界**，
> 不能借用任何"某条蛇的缓存"。缓存会因为它死了而冻结，看起来像功能没生效。

## 27. ★★ 每局换一个世界种子（负责人要求）

### 27.1 负责人要求

> 训练模式，游戏模式请每局种子不同。

### 27.2 改之前是什么状态（两个问题）

| | 改前 |
|---|---|
| `TrainTask::makeArenaConfig` | `ac.spawnSeed = 0u`，注释写"不动全局随机序列，交给调用方管" —— **而调用方从来没管过** |
| `GameScene` | `spawnSeed` 也是 0，只给圈位设了一个 `posSeedOffset` |
| `Arena::reset` | `if (spawnSeed != 0) srand(spawnSeed)` ⇒ 两处都是 0 ⇒ **从不重新播种** |

后果有两条，第二条正是负责人报过的现象：

1. **出生点 / 出生角度 / 食物** 走全局 `rand()`，那是一**条跨局连续的流** ——
   单独重开一局时它们**不重新随机**（不算固定种子，但也不是每局随机）。
2. **圈的种子是固定的**：`orderSeed` / `posSeed` 都取自 `t.seed`（固定）
   ⇒ **很多局的圈位序列一模一样**。负责人报过：
   "很多局都固定那两个同样的位置。"

### 27.3 改法：世界种子统一在 `Arena::reset` 里播种

新增 `ArenaConfig::advanceSeedOnReset`：

| 取值 | 行为 | 谁用 |
|---|---|---|
| `false`（默认） | 每次 reset 都用同一个 `spawnSeed` | **回归工具**（`replay_check` 靠它可复现） |
| `true` | 每次 reset 把种子推一格：`seed = spawnSeed + resetCount` | **训练 / 游戏** |

```cpp
if (m_cfg.spawnSeed != 0u) {
    m_worldSeed = m_cfg.spawnSeed;
    if (m_cfg.advanceSeedOnReset) m_worldSeed += m_resetCount;
    std::srand(m_worldSeed);
    m_sched.orderSeed        = m_worldSeed;             // 圈轮换顺序
    m_cfg.zoneLayout.posSeed = m_worldSeed + 0x9E3779B9u; // 圈坐标（派生一支）
}
++m_resetCount;
```

**★ 为什么必须统一在这一个地方播种**：世界的随机来自四处，
它们必须来自**同一个种子**，否则"同一局可复现"这条性质在调试时就不成立：

| 随机源 | 吃什么 |
|---|---|
| 出生点 / 出生角度 | 全局 `rand()` |
| 食物位置 | 全局 `rand()` |
| 圈轮换顺序（randomOrder） | `ZoneSchedule::orderSeed` |
| 圈坐标（randomPosition） | `ZoneLayout::posSeed` |

**★ 种子仍然是可复现的起点**：第 k 局的种子 = `spawnSeed + k`，
所以同一个任务种子跑出来的"第 k 局"永远相同 —— **对照实验仍然可比**，
只是"每一局不再重复"。

### 27.4 调用方

| 位置 | 改动 |
|---|---|
| `TrainTask::makeArenaConfig` | `spawnSeed = t.seed`、`advanceSeedOnReset = true` |
| `GameScene::rebuildArena` | `spawnSeed = clock()`、`advanceSeedOnReset = true`；删掉 `posSeedOffset`（已由世界种子统一派生） |
| `LiveTrainingScene` | 不用改 —— 它走 `makeArenaConfig`，每局 `Arena::reset` 自动换种子 |
| `replay_check` / `bench_sim` | 不用改 —— 它们不设 `spawnSeed`（= 0），完全保持旧行为 |

> ★ `posSeedOffset` 现在**不再需要**：`Arena::reset` 会把 `zoneLayout.posSeed`
> 对齐到本局的世界种子。留着它反而让"圈的位置"和"世界的种子"来自两个源。
