## 1. ★★★ 先说最重要的：为什么必须先建判据

本轮开始时，项目已经积累了大量"改了参数但看不出效果"的记录（docs/30 第 8 节）。
根因不是不会调参，而是**没有可信的判据**：

- 只看单局回报 → 分不清"在进步"和"在两种模式之间乱跳"
- 只跑一个种子 → 无法区分"这个现象是普遍的"和"这次碰巧如此"
- 只看总回报 → 不知道是哪个分量在主导

所以本轮**先做工具，后做改动**。

### 建了什么

| 工具 | 位置 | 作用 |
|---|---|---|
| 逐帧速率诊断 | `EpisodeRunner.h` | 分清"某项总和很大"是因为**速率高**还是**持续久** |
| 动作次数统计 | `EpisodeRunner.h` | 锁死的客观判据（含 ε-greedy 的随机步） |
| 饥饿状态分桶 | `EpisodeRunner.h` | 余韵/正常/饥饿各占多少帧 |
| 生效帧占比 | `EpisodeRunner.h` | 危险区、饥饿窗口**实际触发**了多少帧 |
| 死因分布 | `train_probe` | 撞墙/撞蛇/饿死/未死 |
| **滑动窗口**（每 100 局） | `train_probe` | 吃食/存活/**动作熵**/每帧速率/死因/步长 |
| `--ablate` | `train_probe` | 同种子因果对照（no-fed / no-approach / no-hunger / no-eat / no-snake） |
| `--seed` | `train_probe` | 多种子复现 |
| 步长诊断 | `nn/network.h` + `Trainer.h` | 梯度范数 / 参数位移 / 参数范数 |

**验证工具本身没改行为**：不带任何新开关跑 400 局，
`fed = 100.3654`、`eat = 13.685` 与改动前**逐位相同**。

## 2. ★★★ 动作熵单独用会骗人（本轮最重要的发现）

观测改成 33 维后，5 个种子的末窗熵：

```
seed11111    熵 0.958   每局吃 6.79   ← 好
seed20260921 熵 0.929   每局吃 0.88   ← 熵高，但学得差
seed22222    熵 0.868   每局吃 7.64   ← 好
seed33333    熵 0.164   每局吃 0.21   ← 锁死
seed44444    熵 0.171   每局吃 0.21   ← 锁死
```

`seed20260921` 的熵 **0.929**，看起来完全健康。但它的动作分布是
`(左0.18 直0.21 右0.62)` **长期不变**，每局只吃 0.88 个。

**这是"熵高但僵化"，与 `seed33333` 的"熵低且僵化"是两种不同的失败**，
而熵这一个数把它们混成了"一个健康、一个失败"。

> ★ **判据必须组合看，优先级**：
> **`吃食数是否还在上升` > `末窗吃食数` > `动作熵`（仅辅助）**

已写入 `docs/90` 第 5 节。

## 3. ★★ 三个被实测推翻的假设（都是我自己的判断）

### 假设 1：「`fed` 是伪装成饱腹感的存活带宽，导致绕圈」

**我的推导**：`fed` 整局积分 = `25 × [min(20,τ_last) − min(20,τ_first)] / 60`，
是个望远镜和，等价于"一口食物买 4.17 秒的命"，所以是生存奖励。

**实测（`--ablate no-fed`，3 种子）**：

```
no-fed 三个种子的末窗熵全部 = 0.169，且从第 200 局锁死后 1300 局不再变化
每局吃：0.09 / 0.03 / 0.10
```

**结论：反了。** 关掉 `fed` 才导致**永久锁死**；`fed` 是当前**唯一**在防止锁死的正信号。

**我漏掉的一环**：我只看了"它奖励什么"（生存），没看"没有它之后回报还剩多少"。
关掉 `fed` 后 `eat` 在整局回报里只值 **+0.5 分 / 共 −32.8**，
而 `die −10` 是**每局固定的、不随行为变化的** ——
**整局回报被压成一个与行为无关的常数，梯度里只剩噪声。**

### 假设 2：「移动的每帧回报为负（因为撞死风险）」

**实测**：代码里**没有任何惩罚移动的措施**。我把所有每帧项逐个查了一遍：

| 项 | 触发条件 | 是移动惩罚吗 |
|---|---|---|
| `hunger` | 剩余饥饿 < 10s | ❌ 与移动无关 |
| `approach` | 靠近最近食物 | 是**奖励** |
| `fed` | 距上次进食 < 10s | 是**奖励** |
| `snake` | 头在敌方 100px 内 | ❌ 是**邻近**惩罚 |
| `die` | 死亡，**每局一次** | ❌ 一次性 |

**死因实测**：饿死 **98%**（no-fed）/ 52%（ctrl），**撞墙只占 5%**。
所以"移动 → 撞死 → 负回报"这条链**不成立**。

**我还错在**：反推"危险区待了 71 帧"时，依赖了"每帧满额"这个**没验证的假设**。
实测是 **13~17% 的帧**都在危险区（300 帧/局），不是罕见事件。

### 假设 3：「`normalizeAdv` 把噪声放大，是 critic 失败的原因」

**实测**：关掉标准化 + 把价值网络 lr 降到 1/5 + 两者同时，
**三种配置在两个种子上一律照样锁死**。假设被证伪。

### ★ 共同原因

**我都在单个种子上做判断。** 同参数下种子间差异能到 30 倍，
单种子结论有一半概率是错的。**这条教训比本轮任何代码都值钱。**

## 4. ★★ 查出的两个观测缺陷（确凿，已修）

### 缺陷 A：食物圈的"距离维"是一个常量

`encoder.h` 的体积注释写着：

```
[20..22]  当前活跃圈：sin(方位) / cos(方位) / 1
```

而中间那段注释却写着"每个圈给 sin/cos + **归一化距离**"，
代码实际是：

```cpp
obs[base + 2] = (slot == 0) ? 1.0 : 0.0;   // 常量！只表示"在哪个槽位"
```

**两处注释互相矛盾，实现跟了头部那个。**
后果：蛇看得见圈的**方向**，不知道圈的**远近**。

> 旁证：`docs/90` 早期记录里有"把信息密度最低的那一维
> `min(1, 圈距离/2000)` 替换成 active" —— 说明这一维**曾经存在**，
> 被替换掉了，但注释和文档没跟着改。

### 缺陷 B：敌人身体与墙混在同一个通道

8 条障碍射线用的掩码把 墙 / 敌身 / 敌头 / 自己 全算作障碍，
网络分不清那是墙、是敌人、还是自己。

**而由此产生一个奖励与观测不匹配的严重不对称**：

| | 有吗 |
|---|---|
| 因为"头靠近敌人身体"被持续扣分（`rSnakeDanger`，实测占 **10% 回报**） | ✅ |
| 观测里能知道敌人在哪并针对性躲避 | ❌ |

`Perception::headToEnemyBodyDist` **算好了但编码从来不读**。
蛇被一个**看不见来源的信号**持续推着走。

### 修法：29 → 33 维

```
[ 0.. 3]  墙/自己：4 方向
[ 4..11]  ★ 敌方身体/头：8 方向（新通道）
[12..19]  食物：8 扇区
[20..23]  速度/长度/朝向
[24..26]  ★ 当前圈：sin/cos/【距离】
[27..29]  ★ 下一个圈：sin/cos/【距离】
[30..32]  队友
```

| 11111 | 0.23 / **0.171 锁死** | **3.57 / 0.958** ✅ |

| **平均** | **3.68 / 锁死 1/5** | **2.33 / 锁死 2/5** |

**平均吃食下降 37%，锁死从 1/5 升到 2/5 —— 这是负结果，如实登记。**

### 为什么保留不回退

1. 它修掉的两个缺陷是**确凿的**（信息本身变正确了）
2. `seed11111`（旧版必锁死的坏种子）在 33 维下变成**最好的**（6.79）
   —— 说明"看不见敌身"确实是个真问题
3. 净负更可能来自**一次动了三个变量**：
   +4 维 / 墙分辨率 8→4 / 敌身新增通道

### 下一步：拆变量

**应该分步验证"只加圈距离"与"只加敌身通道"各自的贡献**，而不是回退。

## 5.5 ★★ 奖励机制改动与多种子验证（2026-09-26 晚）

### 改了什么（负责人决定）

| | 变更 |
|---|---|
| ⑥ | **删除**「贴近敌方身体的每帧惩罚 −0.15」→ **改为**「成功拉开距离 +0.15」（硬阈值+迟滞：进 250px / 出 375px，每次进入只结算一次） |

### 多种子验证（5 种子 × 1500 局，`zone-random`）

| 种子 | 旧机制 末500局吃 / 熵 | 新机制 末500局吃 / 熵 |
|---|---|---|
| 11111 | 0.23 / **0.171 锁死** | 1.43 / 0.427 |
| 20260921 | 7.13 / 0.995 | 2.83 / 1.005 |
| 22222 | 2.13 / 0.746 | 7.78 / 0.822 |
| 33333 | 5.23 / 0.900 | 4.87 / 0.988 |
| 44444 | 3.70 / 0.843 | 0.23 / **0.171 锁死** |

**结论：吃食数持平（3.68 → 3.43，噪声范围内）、锁死数不变（1/5）。净效果中性。**
但**熵普遍上升**（4/5 种子），即"更不确定"了 —— 这在**当前**是负面的
（吃食数没升），但它意味着策略没有塌进确定性动作，**长期可训练性更好**。

### 🔴🔴 本轮最重要的纠正：锁死态是【直行】，不是【转圈】

五项新机制在 5 个种子上**触发次数全部为 0**：

```
逃生奖励触发 0.00 次/局 | 连续转弯扣分 0.0 帧/局
```

**原因查明了，而且它推翻了一条长期以来的错误描述：**

| 种子 | 末窗动作分布 | 判定 |
|---|---|---|
| seed11111 | 左0.05 **直0.89** 右0.06 | 直行 |
| **seed44444（锁死）** | 左0.02 **直0.97** 右0.02 | **直行** |

```
[滑窗 @40]  吃 0.00 | 存活 219.6 | 动作熵 0.185 (左0.02 直0.98 右0.02)
[滑窗 @1500] 吃 0.18 | 存活 208.0 | 动作熵 0.171 (左0.02 直0.97 右0.02)
```

> ★★★ **锁死态的动作分布是【直行 0.97】，不是"转圈"。**
> 2000×2000 地图上全速直行 → **约 3.5 秒后撞墙** → 100% 撞墙死 → 回报锁在 −6。
>
> - `escape` 不触发，因为蛇**根本不靠近敌人**（危险区帧占比 0.00%）
> - **⑩ 连续转弯惩罚也不触发，因为蛇根本不转弯 —— 它一直直行！**
>   **这条机制治的是"绕圈"，而实际病灶是"直行"。**

### ⚠️ 因此这条机制【设计目标与实测病灶不匹配】

负责人要治的是"转圈直到饿死"，而多种子实测显示：
**在 `zone-random` 上，锁死的形态是"直行撞墙"。**
两者都是"策略塌成确定性动作"，但**表现相反**（转圈 vs 直行），
所以针对"转圈"的惩罚对"直行"无效。

**唯一能同时覆盖两种形态的，是"动作熵"本身**（都表现为熵塌到 0.17 附近）。

## 5.6 ★★★ 用规则 AI 当标尺：证明瓶颈在训练链路（2026-09-26 晚）

### 做了什么

1. **训练模式默认改成**（负责人指定）：随机圈 / 3 队 × 2 条 / 90 秒 /
   队0=神经网络、队1=规则AI、队2=敌方网络快照
2. **重写 `RuleBrain`**：优先级从"躲障碍 > 找食物 > 漫游"改成
   **"保命 > 找食物 > 找圈 > 攻击 > 漫游"**

### ★ RuleBrain 重写的核心：接上"一直存在但没人用"的圈方位

旧版只有"躲障碍 > 找食物 > 漫游"。而**食物只在圈里**、
视野半径 ≈512px、圈半径 150px —— 蛇只要不在圈附近，
视野里就**什么都没有**，于是只能漫游，表现就是"傻"。

**而 `Perception.zones` 一直提供全局的圈方位与距离
（`FoodZoneView::bearing` / `distance`，不受视野限制）。
"该往哪走"这个信息一直都在，只是旧版从来没用过。**

新增的两级：
- **找圈**：视野没食物时朝当前活跃圈走；当前圈空窗了就朝下一个圈走（提前出发）
- **攻击**：★ 带优势判定 —— 只在"我的头离对方身体够远、且对方的头离我身体够近"
  时才动手（这正是围猎的几何条件）。无条件冲向敌人等于自杀，
  因为规则是「**我的头**碰到**对方身体**才死」。

### ★★★ 最有价值的数字：规则 AI 是神经网络的 4~7 倍

同一套 Arena / 同一套奖励 / 同一配置（3队×2蛇 / 90 秒）：

| agent | 每局吃 | 存活帧 | 死因 |
|---|---|---|---|
| **规则 AI** | **2.33** | **1203** | — |
| 神经网络（学习中的那条） | **0.17~0.61** | 205~980 | **撞墙 73~79%** |

**神经网络的退化轨迹（800 局）**：

```
[滑窗 @100] 吃 0.31 | 存活 815 | 熵 0.901 (左0.16 直0.21 右0.64)
[滑窗 @600] 吃 0.61 | 存活 379 | 熵 0.889 (左0.19 直0.65 右0.16)
[滑窗 @800] 吃 0.17 | 存活 205 | 熵 0.221 (左0.02 直0.95 右0.02)  ← 锁死成"永远直行"
           死因: 撞墙 73 | 撞蛇 27 | 饿死 0
```

**越训越差，最后塌成"永远直行 → 撞墙"（存活仅 205 帧 = 3.4 秒）。**

### 这条数字为什么重要（它排除了一大堆可能）

它**证明环境本身是能玩的**（规则 AI 用同样的感知、同样的动作空间能吃到 2.33 个）。
所以：

- ❌ 不是"任务太难"
- ❌ 不是"观测不够"（规则 AI 用的是同一份 Perception）
- ❌ 不是"奖励不对"（规则 AI 不读奖励也能吃到 —— 但注意它**不学习**，
  所以这只能说明"行为是可达的"，不能说明奖励形状没问题）
- ✅ **是训练链路**：策略梯度在把这个任务**越训越差**

> ★ **在修好训练之前，任何"加机制 / 调常数"都不该指望有效果。**
> 这是本轮最该被记住的一条。

### 复现方法（写进 docs/90 第 6 节）

把 `task.teamAlgorithms[0]` 临时改成 `"rule"`，
用同一个 `makeArenaConfig` + 同一个 `EpisodeRunner`（trainer=nullptr）跑 300 局。

## 5.7 ★★★ 查出并修掉一个让"训练"完全落空的 bug（2026-09-26 深夜）

### 症状（负责人先观察到的）

> "蓝色蛇（学习中）和敌人蛇（快照版本）的表现差距极大。
>  快照版本真的有一段时间统一一下吗？"

### 根因：全局"待定值"用完不清

```cpp
// NeuralBrain.cpp:25  —— 全局变量
std::string g_pendingEnemySnapshot;

// NeuralBrain.cpp:54  —— 构造函数：只要它非空，就加载快照并【直接 return】
if (!g_pendingEnemySnapshot.empty()) { ...; return; }

// BrainRegistry.cpp:127 —— 创建 nn-enemy 时把它设上
NeuralBrain::setPendingEnemySnapshot("saves/enemy_snapshot.txt");
// ← 从来没有清空过（修复前）
```

**于是它一旦被设上，之后创建的每一个 `NeuralBrain` 都去加载快照** ——
**包括算法 id = `"nn"` 的、学习中的那条蛇。**

按新默认（3 队：nn / rule / nn-enemy）的创建顺序：

| 队 | 算法 id | **实际加载的东西** |
|---|---|---|

## 5.11 ★★★ 找到 escape 恒为 0 的真正根因：`Perception` 的标量字段每帧不重置

### 负责人给的关键线索

> "我亲眼观测到了蛇头 A 进入 B 的危险区域，但是 B 撞死在 A 身上，
>  **A 的 escape 仍然是 0**。而且**哪怕逃离的概率很低，escape 也不应该永远为 0**。"

**这句话直接推翻了我的诊断方向。** 我之前测出"178 次进入、0 次退出"，
据此说"蛇从不活着退出"—— 但负责人亲眼看到 A 明明在危险区里活动过。
**"永远为 0"本身就是一个 bug 信号，不该被解释成"概率低"。**

### 根因

```cpp
// Perception.h —— 只清列表，不清派生标量
void clearLists() {
    grid.clear();
    snakes.clear();
    allies.clear();
    zones.clear();
    // ← hasEnemyInView / headToEnemyBodyDist / enemyHeadToMyBodyDist
    //   / riskEnemyId 【全都没有重置】！
}
```

`PerceptionBuilder::build()` 开头只调 `clearLists()`，于是：

> **敌人一出视野（>512px），`headToEnemyBodyDist` 就冻结在"最后一次看到它时的值"。**

对 escape 的影响是致命的：

| 条件 | 实际行为 |
|---|---|
| 进入：距离 **< 250px** | ✅ 会触发（冻结的读数恰好落在这个区间） |
| 退出：距离 **> 375px** | ❌ **永远不触发**（读数冻死在 250px 以下，再也上不去） |

**所以 escape 恒为 0 —— "进得去、出不来"。**

### 污染范围（不止 escape）

同一个陈旧读数还被这些地方读：
- `RuleBrain::wantBoost()` —— "周围有没有敌人"（决定要不要加速）
- `RuleBrain::canHunt()` —— 围猎优势判定
- `EpisodeRunner` 里 ⑥⑦ 两项奖励的诊断

### 修法

新增 `Perception::resetFrameState()`，在 `PerceptionBuilder::build()` 开头调用：

```cpp
void resetFrameState() {
    hasEnemyInView        = false;
    headToEnemyBodyDist   = 1.0e9f;   // 哨兵 = "视野内没有敌人"
    enemyHeadToMyBodyDist = 1.0e9f;
    riskEnemyId           = -1;
}
```

**★ 为什么单独一个函数，不塞进 `clearLists()`**：
`clearLists()` 的语义是"清列表"，这里是"清派生标量"。
两者生命周期不同（列表靠容量复用，标量靠重算），混在一起会让人
以后加字段时不知道该往哪边放。**分开写，名字即文档。**

### ★ 教训

> **一个"永远为 0 / 永远不变"的读数，第一反应应该是"查它为什么是常量"，
> 而不是"解释它为什么合理地小"。**
> 我上一轮就是这么错的：我把"178 次进入 0 次退出"解释成
> "蛇太弱、活着退不出去"，还据此建议**删掉这个奖励项** ——
> 而真因是一个**每帧不重置的陈旧字段**。

### ★★ 修正：判据从【总路径长度】改成【净位移】（负责人指出）

**负责人原话**：
> "值得注意的是，我们不应该检测移动总距离（一直绕圈也能满足），
>  而应该检查总位移，或一段时间平均坐标的偏移。"

**这是对的，而且它同时解释了 `disp` 为什么恒为 0。**

**我的第一版错在哪**：我用的是"每帧位移的累加"（**总路径长度**）。
而：

> **蛇只要在动，绕一圈的路径长度就有 750px** ——
> 所以"一直绕圈"必然满足"路径 ≥ 阈值"，**惩罚永远不会触发**。

**`disp` 恒为 0 的根因不是"配置没读到"、也不是"蛇动得够多"，
而是我选错了要判的量。**

**改法**：把窗口从"每帧位移"改成"**坐标样本**"，判据改成
**平均坐标偏移**（比单纯"首尾坐标差"更稳）：

```
窗口 = 最近 3 秒的坐标样本
前半段平均坐标 (x̄1,ȳ1)  vs  后半段平均坐标 (x̄2,ȳ2)
净位移 = |(x̄2,ȳ2) − (x̄1,ȳ1)|

绕圈    → 平均值几乎不动 → 净位移 ≈ 0   → **正确触发**
直线赶路 → 平均值明显平移 → 净位移大     → 不触发
原地抖  → 平均值不动                     → 正确触发
```

**`dispMinPx` 从 450 改成 120**：
判的是"**有没有换地方**"，不是"走得够不够快"。
绕直径 170px 的圈时，3 秒净位移可能只有几十像素 —— 那正是要罚的。
所以门限必须**远小于**正常赶路的距离（750px）。120px ≈ 半秒路程。

## 5.13 ★★★ 找到了真正的瓶颈：奖励信号的噪声是有效信号的 15 倍

### 负责人提出的疑问

> "我怀疑神经网络根本不会管 reward，因为哪怕顶着高惩罚它也会一直转圈。
>  你仔细检查一下，惩罚机制真的在倒逼神经网络学习吗？神经网络有在关注 reward 吗？"

### 实测：回报的标准差

```
（800 局，修复快照 bug 之后的数据）
回报:  min −10.0 | p25 −6.5 | 中位 20.2 | p75 50.1 | max 388.1
均值 28.9   标准差 44.5   → 标准差是均值的 1.54 倍
```

| 项 | 单次幅度 | 相对标准差(44.5) |
|---|---|---|
| 吃一个食物 | +3 | **0.07** |
| 死亡罚 | −10 | **0.22** |
| `disp` 一个完整触发周期 | −9 | **0.20** |

### 结论：**"用惩罚倒逼学习"在当前训练器下【结构上走不通】**

**① 恒定的每帧惩罚，梯度约等于 0**

`adv_t = G_t − baseline`。`disp` 一旦触发，就**几乎在"饿着"的每一帧都扣** ——
它变成了一个**跨轨迹近似恒定**的大常数（就像每局固定的 `die −10`）。
而**REINFORCE 里恒定项会被 baseline 完全吸收，贡献的梯度是 0**。

所以"顶着 −20 分/局的 `disp` 继续转圈"**不是网络无视 reward** ——
是那笔惩罚在数学上**根本进不了梯度**。它只改变了回报的绝对高度。

**② 即便不恒定，噪声也淹没它**

我们真正在意的动作差异是 **+3 量级**，而局间噪声是 **44.5** —— **差 15 倍**。

**③ baseline 是标量，而且跨不同时长相减**

```cpp
m_baseline = 0.95 * m_baseline + 0.05 * m_lastReturn;   // 标量，跨局
```
每局长度差异巨大（实测 200~3600 帧），所以 `adv` 里混进了
"这局活了多久"的巨大噪声。**标量基线减不掉"这个状态本来就该得多少分"。**

### 网络到底有没有在关注 reward？—— **有，但只有 `eat` 那条路有效**

真实发生过的策略变化（都是实测，不是猜）：
- 动作空间加加速 → **加速占比 43% → 67%**（学会了用加速）
- 关掉 `fed` → 立刻锁死（熵 → 0.169）
- 修快照 bug → 熵 0.221 → 0.95~1.02（不再退化）

**所以 reward 进得去网络。** 但：
```
eat(+3)          → 瞬间、可归因到"吃那一步"     → ★ 唯一有效的学习信号
fed              → 与存活时长相关，弱可归因
disp/hunger/die  → 近似恒定或一次性            → 梯度≈0 或 只教"别死"
```

**"转圈"顽固的原因**：转圈不撞墙、能活满一局（`fed` 照拿），而"去吃"要冒险。
在 advantage 被 44.5 的噪声淹没时，**"维持现状"的稳定性压过了"冒险去吃"的正梯度**。

### 决定：改用 actor-critic（价值网络 baseline）

代码**早已写好并保留**（`LearningMode::Critic` / `updateCritic` / `ValueNet`）。

> ⚠️ **我上次测它是失败的**（锁死率 20%→80%），但那个结论**已经作废** ——
> 那批实验是在**"学习中的蛇其实在执行敌方快照"这个 bug 存在时**跑的
> （见 5.7 节）。学习中的蛇根本没有执行被训练的网络，所以那次测的不是 actor-critic。

**本次接上的两个缺口**（都属"一个能力只在一条路径上接了"）：

| 缺口 | 说明 |
|---|---|
| **训练模式没有 actor-critic 开关** | 原来只有命令行 `--learner critic` 能开，而负责人看的是**游戏内训练模式** —— 于是"换成 actor-critic 试试"在训练模式里**根本做不到**。现在 `LiveTrainingScene` 直接设为 `Critic` |
| **面板看不到 critic 是否在学** | 新增一行 `critic: V-target corr / MSE / advSD` |

**判据（面板上那一行）**：
**`V-target corr` 必须明显为正**。持续接近 0 = 价值网络没学到 = GAE 是空的
= 换了算法也没用。**那时应该停下来查，而不是继续堆机制。**

## 5.14 ★★★ 负责人报「critic 恢复到 0.5，蛇仍顶着惩罚原地转圈」→ 查出两个确凿的实现缺陷

### 负责人原话

> "critic 正常恢复到 0.5 左右，但是蛇仍然顶着惩罚原地转圈，
>  disp 一直在逐渐增加，加到 20 多，reward 一直在递减，变成负数"

### 我一开始的误判（先记下来）

我看到 `disp` 只有 20 多分，算出"20 ÷ 3.0 = 7 帧触发，相对 5400 帧的局微不足道"，
**据此准备建议"disp 太小了，调大它"**。这个方向是**错的**，而且差点又浪费一轮。

真正该做的是：**在被报出来的读数里找"和代码算出来的不一致"**。
`disp = 20` 反推是 7 次触发 —— 而"饿着转圈"每连续 3 秒就该触发一次，
90 秒的局本该触发**几十次**。**这个数量级的矛盾就是线索。**

顺着它查下去，找到两个缺陷。

---

### 缺陷 #46：`maxStepsPerEpisode = 4096` < `maxTicks = 5400`

```cpp
// Trainer.h（修正前）
int maxStepsPerEpisode = 4096;                     // ← 太小

void pushStep(const double* obs, int action) {
    if (m_steps.size() >= maxStepsPerEpisode) return;   // ← 静默丢弃，不报错
    ...
}
void pushReward(double r) { m_rewards.push_back(r); }   // ← 没有上限！
```

随机圈任务 `maxTicks = 90 * 60 = 5400`，于是：

| | 值 |
|---|---|
| `m_steps.size()`（观测 + 动作） | **4096**（封顶） |
| `m_rewards.size()`（奖励） | **5400**（照涨） |
| `finishEpisode()` 里 `T` / `R` | 4096 / 5400 |
| 按 `T` 对齐后**实际参与学习** | **前 4096 帧** |
| **被丢掉** | **后 1304 帧（24% 的局）+ 死亡那一笔 −10** |

**为什么这正好解释负责人看到的现象**：
丢掉的尾巴**恰恰是 `hunger` 和 `disp` 累计最多的那一段**
（越到后面越饿、`disp` 越在触发）。
**越是需要被纠正的行为，越是被丢干净。**

而且它是**静默**的：不崩、不报错，现象只是"学不会"。

**修法**：
- `maxStepsPerEpisode` 4096 → **8192**（≥ 5400 且留余量；内存 8192 × ~280B ≈ 2.2 MB）
- `pushReward` **同步加上限** —— 奖励和观测必须同长，否则拿错位的奖励去更新（比丢更糟）
- 新增 `lastEpisodeTruncated` 标志 + `stderr` 一次性告警：**以后再截断会立刻看见**

---

### 缺陷 #47：`foodScoreUnit` 错 3 倍 → 吃一个食物只给 +1.0

```cpp
// TrainTask.h（修正前）
// ★ 取值 3：和世界规则的 Constants::FOOD_SCORE 一致（普通食物 3 分）
double foodScoreUnit = 3.0;
```

**但 `Constants::FOOD_SCORE` 早就是 `1`**（`CORPSE_FOOD_SCORE` 才是 3）。
注释没跟着改，分母就照着错的注释写死了。

`EpisodeRunner` 算的是 `rEat × (实际得分 / foodScoreUnit)`：

| | 设计意图 | 修正前 | 修正后 |
|---|---|---|---|
| 普通食物（`FOOD_SCORE = 1`） | +3.0 | **+1.0** ❌ | **+3.0** ✅ |
| 尸体食物（`corpseScore = 5`） | +15.0 | **+5.0** ❌ | **+15.0** ✅ |

**★ 教训：注释里写具体数值会腐烂。**
凡"必须和 XX 保持一致"的常数，注释只该写"去看 XX"。

### ★★★ 把奖励换算成「秒」之后，一切都说通了

这是本次最有价值的一张表。**所有奖励都以"能买回几秒生存"来衡量**：

| 项 | 数值 | 折算 |
|---|---|---|
| `hunger` 封顶 | −3.0/帧 | **−3.0/秒** |
| `disp` 触发时 | −3.0/帧 | **−3.0/秒** |
| 饿着 + 原地转圈（叠加） | −6.0/帧 | **−6.0/秒** |
| `fed` 余韵（2.5 × 10s ÷ 2） | 一次性 | +1.25 |
| **吃一个食物（修正前）** | **+1.0** | **买回 0.17 秒** ❌ |
| **吃一个食物（修正后）** | **+3.0** | **买回 0.5 秒** ✅ |

> **修正前，蛇必须每 0.17 秒吃到一个食物才刚好不亏 ——
> 而食物生成间隔是 0.5 秒。
> 所以"饿着转圈"在算术上稳赢，"去找吃的"稳亏。**

**所以"顶着惩罚原地转圈"根本不是神经网络学不会 ——
是奖励把正确答案定义成了错的。** 这一条直接回答了负责人的疑问
（"惩罚机制真的在倒逼神经网络学习吗？"）：**没有，而且原因不在"惩罚太小"，
在"奖励基准算错了 3 倍"。**

修正后要求"每 0.5 秒一个"，和 `FOOD_SPAWN_INTERVAL = 0.5` 对上了 ——
**这才是设计意图的量级。**

### 关于 `V-target corr = 0.5`：它证明的比看起来少

**必须区分两件事**：

| 指标 | 衡量的是 |
|---|---|
| `V-target corr` | **critic 学没学会**（能不能预测回报） |
| 吃食数 / 存活 | **actor 有没有变好** |

0.5（R²=0.25）说明 V 能预测回报的 25%，而它最容易预测的东西是
**`hungerLeft`** —— 因为饥饿窗口里回报主要就是 `hunger` 的累积。
**critic 变好只让 `adv` 少了一部分噪声，不能让 `adv` 的方向变对。**

所以：**0.3 → 0.5 是真进步，但下一步不该继续优化 critic。**
当时的证据就是"critic 好了，food 却没涨"。

### 一个还没动、但必须知道的结构性限制

```
γ = 0.99、60 fps  →  有效视野 γ^100 ≈ 0.37  →  约 1.67 秒
1.67 秒 × 250 px/s = 417 px     ← 视野内"值得为它行动"的最远距离
食物感知归一化半径   = 800 px   ← 网络"看得见"的距离
```

**中间 417~800px 那一段，网络看得见食物、却学不到"该往那儿走"。**

这解释了一个反复出现的困惑：观测里明明有圈方位（`obs[24..29]`）、
感知里有 8 扇区食物方向，**方向信息是全的，但蛇就是不朝食物走**。
**信息不是瓶颈，"奖励能传多远"才是瓶颈。**

三个候选方向（**设计决策，需负责人拍板，不要擅自改**）：

| 选项 | 做法 | 代价 |
|---|---|---|
| 甲 | 让食物更近更密（训练圈半径调大 / 食物成串生成），压进 417px | 任务变简单，未必迁移到 3000² 地图 |
| 乙 | `γ` 0.99 → 0.995（3.4s）或 0.999（17s） | 方差上升、收敛变慢 |

## 5.15 ★★★ 负责人驳回了我的诊断，并且他是对的 —— 真因是熵项符号写反

### 负责人原话（这一轮最重要的一段）

> "你在开玩笑吗？是奖励机制的问题？**哪怕蛇是随机乱动最后一头撞死
>  也比原地绕圈得到的 reward 更高！**最开始完全没有训练的时候，
>  reward 至少是正的，结果越训练 reward 越小，直到变成负数，
>  其中完全是原地旋转扣的分。**它为什么如此钟爱旋转以至于它宁愿一直扣分！！**"

### 我上一轮错在哪

我上一轮给的解释是"`foodScoreUnit` 错了 3 倍，所以觅食在算术上是亏的，
蛇转圈是理性选择"。**这个解释是错的，而且错在一个很基本的地方：**

> **一个算小了 3 倍的常数，会让所有策略的分数【等比】缩小，
> 但绝不可能让策略【单调变坏】，更不可能让"未训练"优于"训练过"。**

负责人举的反例一针见血：**随机乱动最后撞死** 与 **原地绕圈** 两者的
奖励同样被那个常数影响，所以"标定错 3 倍"根本解释不了前者为什么更好。

> ★ **教训：「某个常数算错了」只能解释「水平不对」，解释不了「趋势不对」。**
> 看到"越训越差"，第一反应该是去找**"哪一项梯度在系统性地推策略"**，
> 而不是去调奖励数值。我上一轮恰恰反过来做了。

---

### 真因（缺陷 #48）：`addEntropyGrad` 的符号是反的

```cpp
// Trainer.h（修正前）
//  熵 H = −Σ pᵢ·log pᵢ。我们要【最大化】H，等价于对 −H 做梯度下降。
//  d(−H)/dz 的逐元素形式：entropyCoef · (−pᵢ) · (log pᵢ + 1)
void addEntropyGrad(...) const {
    g.a[i] += entropyCoef * (-p) * (std::log(p) + 1.0);   // ← 用的是 (−p)
}
```

**注释写的推导是对的，代码用的是它的相反数。** 推导：

```
H        = −Σⱼ pⱼ·log pⱼ
∂H/∂zᵢ   = −pᵢ·(log pᵢ + 1)
∂(−H)/∂zᵢ = +pᵢ·(log pᵢ + 1)      ← 应该加这个
```

送进 `backward()` 的向量会被当作 ∂L/∂z 做**梯度下降**（`step` 里是 `w -= lr·g`），
所以"最大化熵"要加的是 **`+pᵢ(log pᵢ + 1)`**。

**数值自检**（改完可以拿它验证）：

| | 值 |
|---|---|
| 6 个动作均匀时 `p = 1/6` | |
| `log p + 1` | `1 − log 6 = −0.7918` |
| **正确的项** `+p(log p+1)` | **−0.1320**（负） |
| **修正前的项** `−p(log p+1)` | **+0.1320**（正） |

**方向完全相反。** 也就是说 `entropyCoef = 0.1` 这一项
**一直在【最小化】熵 —— 主动把策略推向确定化**。

### 为什么它正好解释"越训越差"

| 观察 | 熵项符号反转能否解释 |
|---|---|
| 未训练（随机策略）反而更好 | ✅ 此时策略还接近均匀，熵项在把均匀分布推开 |
| 训练越久 reward 越小 | ✅ 策略越确定 → 熵项越大 → 更正反馈，**单调恶化** |
| 最后"钟爱旋转"、锁死 | ✅ 坍缩到少数动作后，策略梯度的 ∇logπ → 0，**只剩熵项在动** |
| 与奖励常数无关 | ✅ 它是**唯一一个不含任何任务信息、却每局都朝确定化推**的项 |

**所以"它为什么如此钟爱旋转以至于宁愿一直扣分"的答案是：
因为有一个梯度项在每局都把"别犹豫、选那个动作"当成目标，
而这个目标和吃饭、活命完全无关。** 策略梯度在噪声里挣扎，
熵项却在稳定地、单向地朝确定化推 —— 久而久之只剩它在起作用。

### 修法与新增的判据

| 改动 | 说明 |
|---|---|
| `addEntropyGrad` 符号 | `(−p)` → `(+p)`，符合它自己注释里的推导 |
| 新增 `Trainer::lastEntropyGradNorm` | 量出**熵项单独**贡献的梯度范数 |
| 新增 `measureEntropyGradNorm()` | 用一份 scratch 网络走一遍 backward，**不改主网络** |
| 面板 + `train_probe` | 显示"熵项占总梯度百分比"，**>30% 告警** |

**判据**：熵项应当**远小于**总梯度。
占比一旦不小，就说明策略很大程度上是被熵项推着走的 ——
而熵项只喊"别太确定"，不含任何任务信息。

> ★ 这一条判据的价值超过本次任何代码：它把"策略到底被谁推着走"
> 从一句争论变成了一个可以读出来的数。

### 缺陷 #49：队友其实一直是一份"与训练无关的旧权重"

> 这属于 docs/90 里"回报标准差 44.5"那类问题的一部分，而且它不是随机噪声 ——

> 这里 0.25（每帧）看起来比 0.45（每次）小，实际强度却是它的几十倍。

### 途中踩的坑（记下来）

**坑 1：`tick()` 拿不到 `p`。**

感知对象只在 `decide()` 那一次调用里存在。
我第一版在 `tick()` 里直接写了 `p.self.headToWallDist`，编译必然失败。
正确做法是沿用这个文件已有的模式：**`decide()` 抄下本帧要用的感知字段
（`m_stepWallDist`），`tick()` 只结算奖励**。
这和 `m_stepSnakeDist` / `m_stepHungerLeft` 是同一个套路 —— 加字段时跟着它们放，
就不会走错。

**坑 2：把辅助函数写成函数内的局部 lambda，工厂 lambda 捕获不到它。**

第一版我把 `makeSnapshotBrain` 写成了 `registerBuiltinBrains()` 里的局部 lambda：

```cpp
auto makeSnapshotBrain = [](const char* p) { ... };

reg.reg(info, [] { return makeSnapshotBrain("saves/enemy_snapshot.txt"); });
//              ~~ 没有捕获 → 编译报 "makeSnapshotBrain is not captured"
```

`reg.reg()` 的工厂参数是 `std::function<...>`，而传进去的是个**无捕获** lambda，
它引用不到外层局部变量。

**修法：移到文件作用域的匿名 namespace，做成普通函数。**
它本来就不依赖任何局部状态，放文件作用域最干净 ——
比"给外层 lambda 加 `[&]` 捕获"更好（不引入生命周期疑问）。

> ★ 教训：**要交给 `std::function` 存起来的 lambda，不能依赖它所在函数的局部变量。**
> 这类"看起来能编译"的写法只在无捕获时才成立，很容易忘。
