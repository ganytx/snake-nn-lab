## 1. ★ 最重的一个发现：`EpisodeRunner` 的哨兵值 bug

### 症状

用新加的「奖励构成」输出跑 ZoneMini，结果荒谬：

```
【训练后 · 贪心评估】总回报 631.07
   zone       628.9064    99.66%     ← 一项占了 99.66%
   alive        1.8000     0.29%
   eat          0.0000     0.00%
```

**`zone`（靠近最近食物的塑形，系数只有 0.02）独自给出 628 分。**

### 怎么看出它不对

```
628 分 ÷ 0.02 = 31400 像素  ← 要"累计靠近 31400 像素"
而一局 900 帧 × 4.17px/帧 = 3753 像素
```

**差 8.4 倍，物理上不可能。**

### 定位

那时候还没有「奖励构成」输出，所以先加了探针（`approachFirstDist` 等），
它立刻打出：

```
首帧距离 31622.8   单帧最大变近 31325.1
```

`0.02 × 31325 = 626.5` —— **正好是那 628 分的来源**。
而 `31622.8 = sqrt(1e9)`，是**哨兵值的平方根**，不是一个距离。

### 根因

```cpp
double best = 1.0e9;              // 哨兵 = "还没找到食物"
for (...) if (d2 < best) best = d2;
if (best < 1.0e18) {              // ← 门限比哨兵大 10 亿倍！
    m_stepZoneDist = std::sqrt(best);   // 哨兵自己通过了检查 → sqrt(1e9) = 31622.8
}
```

**语义想表达的是"有没有找到食物"，写法却成了"这是不是一个有限数"。**
哨兵 `1e9` 自己就满足 `1e9 < 1.0e18`，于是**全图没有食物时**（每局开局必然如此）
它走进"有食物"分支，把距离设成 31622.8；下一步恢复正常（几百），
差分就是 31312 → **一步白送 626 分**。

### 后果有多大

- 一局总回报里 99.6% 是**纯 bug 常数**，与蛇的任何行为无关
- 它把 advantage 放大约 600 倍，**彻底淹没觅食梯度**
- **在此之前所有"奖励调参"的结论全部无效** —— 这就是"调了七八轮没效果"的真正原因

### 修法

让**哨兵和门限是同一个数**，并加显式的 `foundFood` 标志：

```cpp
constexpr double NO_FOOD_D2 = 1.0e18;
double best = NO_FOOD_D2;
bool   foundFood = false;
for (...) if (d2 < best) { best = d2; foundFood = true; }
if (foundFood) { ... } else if (act >= 0 && n > 0) { ... 回退到圈心 ... }
```

### 教训

1. **"物理上不可能"的数要立刻停下来查。** 628 分对应的像素数超过一局能走的路程，
   这就说明它不可能是距离。
2. **哨兵值和门限必须是同一个量级**，否则哨兵会自己通过检查。
   更稳的写法是**不用哨兵**，直接用显式的 bool。
3. **总回报是一个和，不是一个数。** 本轮是靠"奖励构成"才发现的 ——
   而**命令行工具以前根本没有这个输出**，本轮补上了。

## 2. 负责人定的新奖励机制（8 项 → 5 项）

### 旧机制的三个结构性问题（不是调参能解决的）

| # | 问题 | 后果 |
|---|---|---|
| ① | 死亡只罚 −0.5，而"墙边每帧 −0.5"一秒就 −30 | **撞死成了止损**，最优策略变成"早点死" |
| ② | 六项塑形全是差分 `k·(prev−cur)` | 整局**望远镜求和只剩"首末距离之差"**，中间路径全抵消 → 教不会"怎么走" |
| ③ | 目标是"最近的那一个食物"，吃掉它 → 换成更远的 → 距离跳变 | 差分大负数（实测扣 2.6~7.2），而 eat 只给 +1.0 → **吃食物净收益为负** |

### 新机制（`src/rl/TrainTask.h`）

```
① 死亡       −10.0      死亡必须让整局努力白费，严格劣于任何其它选择
② 吃到食物   +3.0       唯一的、压倒性的正收益来源
③ 饥饿       0 → −3     剩余 10s 内线性加深，封顶 −3
④ 靠近食物   +0.01×Δd   只给方向，不给分数
⑤ 吃饱余韵   +5 → 0     吃到后 10s 内每秒递减
```

**刻意删掉的**：存活奖励（它奖励"耗时间"而不是"做事"）、
墙体惩罚、蛇危险区、包围奖励（墙的代价由死亡表达）。

### ④ 保留了一个关键保护

**目标换了就不结算这一步的差分**（用目标位置是否相同判定）。
否则"吃掉眼前的食物"会让目标切换到更远的那个 → 距离跳变 → 被扣分。
实测每局约 6~9 步会踩到。

## 5. 本轮踩的坑（都是我自己引入的）

| 坑 | 现象 | 教训 |
|---|---|---|
| **`windows.h` 进了 `network.h`** | 报一片 "expected primary-expression before '>' token"，**错误行号指向几百行之前** | windows.h 定义 `IN`/`OUT` 宏，而 NN 层模板参数**就叫** IN/OUT → 宏替换撕碎声明。**windows.h 只能待在 Checkpoint.cpp** |
| **`std::u8string` / `char8_t` 是 C++20 的** | `'u8string' is not a member of 'std'` | 本项目是 **C++17**。要用 `MultiByteToWideChar(CP_UTF8)` 显式转 |
| **`sf::String::toUtf8()` 返回 `basic_string<sf::Uint8>`** | `could not convert ... to 'basic_string<char>'` | SFML 2.6 就是这样，要显式转一次 |
| **删死代码时多删了一个 `}`** | 报一片 "class does not have any field named ..." | 用括号计数逐段核对，别靠眼看 |
| **PowerShell 脚本执行策略被禁用** | `cannot be loaded because running scripts is disabled` | 用 `ReadAllText` + `Invoke-Expression` 内联执行 |
| **PowerShell 读 UTF-8 源文件中转乱码** | 边界校验看到乱码，差点误判 | `[System.IO.File]::ReadAllLines(path, UTF8)` 显式指定编码 |
